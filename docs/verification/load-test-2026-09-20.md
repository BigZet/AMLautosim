## 1. Система и способ доступа

```
Браузер → NiceGUI (:8080, /play и /admin) → FastAPI (:8000) → PostgreSQL 16
```

Учебный симулятор AML: участник собирает цепочку финансовых операций, FastAPI считает
ресурсы и риск, организатор управляет игрой и рейтингом.

**Важно для методики.** На периметре nginx (`deploy/nicegui.nginx.conf`) закрывает REST наружу:

```nginx
location ^~ /api/ { return 404; }
location = /docs { return 404; }
location = /redoc { return 404; }
location = /openapi.json { return 404; }
```

Проверено с внешнего хоста: `GET https://amlplay.ru/api/v1/health/live` → **404**.
Наружу торчит только NiceGUI. Значит нагрузочный тест через REST невозможен в принципе —
нагрузка обязана идти **через настоящий транспорт UI: socket.io поверх WebSocket**.
Каждый виртуальный пользователь — живой клиент в памяти UI-процесса, как настоящий браузер.

### Устройство драйвера нагрузки

Написан headless-клиент, повторяющий протокол NiceGUI 3.16.0:

1. `GET /play/register` — из HTML извлекается `client_id` и полное дерево элементов
   (блок `parseElements(String.raw...)`) вместе с `listener_id` каждого обработчика.
2. Подключение к `/_nicegui_ws/socket.io` с query-параметрами
   `client_id`, `tab_id`, `document_id`, `next_message_id=0`, `implicit_handshake=true`.
   `tab_id` и `document_id` генерирует клиент — см. `nicegui/static/nicegui.js:408-416`.
3. Ввод в поля: событие `update:value` для `nicegui-input`, пара `update:modelValue` + `blur`
   для `q-input`. Нажатие кнопки — событие `click`. Аргументы передаются JSON-строками,
   см. `nicegui/client.py:396-404`.
4. Редирект после успешного входа приходит событием `open` с телом `{"path": "/play"}`
   (`ui.navigate.to` → `client.open`), **не** через `run_javascript`.

То есть это не синтетический HTTP-флуд, а воспроизведение действий реального браузера.

## 4. Диагноз: почему отказ при CPU 35%

Наблюдение владельца стенда: **в момент отказа CPU хоста поднимался максимум до 35%,
RAM и сеть в пределах нормы.** Это исключает нехватку ресурсов и указывает на
фиксированные очереди и семафоры. Три кандидата по убыванию вероятности.

### 4.1 Пул соединений к БД: 15 штук, таймаут 30 с — главный подозреваемый

`src/aml_workshop_simulator/db/session.py` создаёт движок **без единого параметра пула**:

```python
_engine_kwargs: dict[str, object] = {
    "echo": settings.ECHO_SQL,
    "pool_pre_ping": True,
}
if settings.DB_POOL_DISABLED:          # по умолчанию False
    _engine_kwargs["poolclass"] = NullPool

async_engine = create_async_engine(settings.database_url, **_engine_kwargs)
```

Значит действуют дефолты SQLAlchemy `QueuePool`:

* `pool_size=5`
* `max_overflow=10`
* следовательно **потолок 15 одновременных запросов к БД на весь API-процесс**
* `pool_timeout=30` — ожидание свободного соединения, после чего исключение

Сходится по трём независимым уликам:

1. Зависания в тесте назывались ровно **«нет ответа за 30 с»** — совпадает с `pool_timeout=30`.
2. Превышение таймаута пула поднимает исключение → зафиксирован **HTTP 500** на `GET /play`.
3. **CPU простаивает**, потому что запросы стоят на семафоре, а не считают.

Дополнительно `pool_pre_ping=True` добавляет лишний round-trip к БД на каждый чекаут
соединения — под конкуренцией усугубляет.

Единственная существующая настройка — булев `DB_POOL_DISABLED`
(`src/aml_workshop_simulator/core/config.py:32`). Ручек размера пула нет вообще.

### 4.2 Фоновый опрос, линейный по числу открытых вкладок

`src/aml_workshop_simulator/ui/nicegui/app.py:340`:

```python
ui.timer(3, screen.poll)
```

На **каждого** подключённого участника — опрос `GET /rounds/current/state` раз в 3 секунды,
плюс запрос лидерборда не чаще раза в 3 с, когда он доступен
(`participant.py:644-660` на задеплоенной ветке).

При 45 участниках это **15 req/s только холостого опроса**, и каждый такой запрос берёт
соединение из тех самых 15. Базовая нагрузка растёт линейно по числу открытых вкладок,
даже если все участники просто смотрят в экран и ничего не делают.

Плюс `participant.py:642`:

```python
ui.timer(0.3, self.tick)
```

45 клиентов дают 150 запланированных колбэков в секунду на единственный event loop UI.
Каждый дёшев — реальный вызов API происходит только при `dirty` или устаревшем preview,
пороги `age >= 0.4` и `age >= 1` (`participant.py:1294-1317`) — но в сумме с сериализацией
70-килобайтного JSON на клик добавляет джиттер.

### 4.3 35% агрегата может быть одним выжатым ядром

`docker-compose.yml`: оба сервиса запускаются **без `--workers`**:

```yaml
api:
  command: >-
    sh -c "python -m scripts.seed_database --wait-for-db --migrate
    && exec uvicorn src.aml_workshop_simulator.api.main:app --host 0.0.0.0 --port 8000"
```

Один процесс и один event loop у API, столько же у UI. На 4-ядерной машине одно полностью
занятое ядро даёт 25% агрегата; 35% ≈ 1,4 ядра — ровно картина «два однопоточных процесса
упёрлись в свой потолок, остальная машина спит». Агрегатный CPU по хосту этого не показывает
в принципе, нужен per-process.

### 4.4 Что проверено и исключено

* **Блокировки строк в БД не сериализуют участников.** Запись сценария берёт `FOR SHARE`
  на строку раунда (`services/scenarios.py:62,102`, `services/participants.py:124`),
  а `FOR UPDATE` — только административные операции (`admin_rounds.py`, `scoring_run.py`).
  Разделяемая блокировка участникам друг друга не мешает. Блокировка строки пользователя
  (`db/queries.py:36-38`) — per-user, не глобальная.
* **Lockout по входу ни при чём:** счётчик неудачных попыток персональный
  (`services/authentication.py:98-120`), разные синтетические пользователи его не задевают.
* **Пул httpx UI→API не упирается первым:** `max_connections=80`,
  `max_keepalive_connections=30`, таймаут 15 с / connect 5 с (`ui/nicegui/client.py:31-36`).
  Шире, чем пул БД, значит упрётся позже.

## 5. Как подтвердить диагноз — три команды под нагрузкой

Запускать **во время** повторного прогона 45 VU.

**Гипотеза 4.3, event loop против железа:**

```bash
docker stats --no-stream
```

Если контейнер `ui` или `api` висит около 100% при простое хоста — упёрлись в один поток.

**Гипотеза 4.1, пул БД:**

```bash
docker compose exec db psql -U aml -d aml_simulator -c "SELECT state, wait_event_type, wait_event, count(*) FROM pg_stat_activity WHERE datname='aml_simulator' GROUP BY 1,2,3 ORDER BY 4 DESC;"
```

Если активных соединений ровно ~15 и дальше не растёт при росте нагрузки — пул подтверждён.

**Прямая улика в логах:**

```bash
docker compose logs api --since 10m | grep -iE "timeout|QueuePool|500"
```

Строка вида `QueuePool limit of size 5 overflow 10 reached, connection timed out`
закрывает вопрос.

## 6. Предлагаемые действия

### 6.1 Задать пул БД явно — самое дешёвое и, вероятно, самое результативное

`src/aml_workshop_simulator/db/session.py`:

```python
_engine_kwargs: dict[str, object] = {
    "echo": settings.ECHO_SQL,
    "pool_size": settings.DB_POOL_SIZE,          # предлагается 20
    "max_overflow": settings.DB_POOL_OVERFLOW,   # предлагается 20
    "pool_timeout": settings.DB_POOL_TIMEOUT,    # предлагается 5
    "pool_recycle": 1800,
    "pool_pre_ping": True,
}
```

с соответствующими полями в `core/config.py` и `.env.example`.

Короткий `pool_timeout` важен не меньше размера пула: сейчас перегрузка выглядит для
участника как «сайт завис на 30 секунд», а должна выглядеть как быстрая понятная ошибка
с возможностью повтора. **Интерфейс к этому уже готов:** в нём есть скрытая кнопка
«Повторить запрос» и обработка статусов 408/429/5xx (`participant.py:1151`).

### 6.2 Запустить API в несколько воркеров

`docker-compose.yml`, сервис `api`: добавить `--workers 4`.

Состояния в процессе API нет, сессии лежат в БД — масштабируется свободно.
**`ui` обязан остаться в одном процессе:** NiceGUI держит дерево элементов и объекты
`Client` в памяти, многопроцессность сломает его без sticky-сессий и общего состояния.

Арифметика соединений: 4 воркера × (`pool_size` 10 + `max_overflow` 10) = 80 при дефолтном
`max_connections=100` образа `postgres:16` — влезает впритык. Для 4 × 20 = 160 нужно
поднимать `max_connections` до 200 и соответственно `shared_buffers`.

### 6.3 Убрать холостой опрос

Соединение уже есть — WebSocket. Смену статуса раунда логичнее **толкать** со стороны
организатора в сокет, чем опрашивать каждым участником раз в 3 секунды.
Минимальный вариант без переделки архитектуры: увеличить интервал, когда раунд в состоянии
`draft` или `completed` — там опрашивать попросту нечего.

### 6.4 Сократить payload на клик

Сделать так, чтобы мутация цепочки обновляла только затронутую карточку и сводку,
а не перестраивала весь список (`render_chain`, `participant.py:932`).
Бьёт сразу по двум местам: меньше JSON на event loop UI и меньше вызовов к API.
Сохранить работоспособность кнопок перестановки, копирования и удаления, а также подписей
таймлайна. Проверять замером объёма обновления при цепочке из 8 операций до и после.

### 6.5 Перемерить

После 6.1 и 6.2 повторить прогон на 45 и 60 VU. Если пул был тем самым местом,
потолок уедет заметно, и станет видно следующее узкое горлышко.

## 7. Функциональный проход UI

### Работает корректно

* **Валидация регистрации.** При коротком пароле и некорректном email показываются все три
  ошибки полей одновременно: «Имя должно содержать от 2 до 120 символов.»,
  «Введите корректный email.», «Пароль должен содержать от 10 до 128 символов.».
  При несовпадении паролей проверка срабатывает раньше остальных и показывает
  «Пароли не совпадают» отдельно.
* **Доступность.** У всех инпутов есть `aria-label`, связанный `label[for]` и корректный
  `autocomplete` (`name`, `username`, `new-password` / `current-password`), `lang="ru"`.
* **Мобильная вёрстка.** Проверено на 375×812, форма входа не разъезжается.
* **Пустая форма входа** отвечает «Укажите email и пароль.», в том числе под нагрузкой 15 VU.
* **`/about`** — полное и внятное описание игры: четыре шага и карта интерфейса.
* **Полный игровой путь пройден до конца:** 7 операций, цель 360 000 ₽ исходящих закрыта на
  100%, диалог подтверждения «Отправить сценарий окончательно? После отправки изменить
  цепочку или отправить её повторно нельзя.», **отправка за 1 571 мс**, далее read-only
  список отправленных операций с контрагентами и назначениями.
* **Автосохранение** отображает статус «Сохранено».
* **Обработка отрицательного баланса сделана хорошо.** При уходе баланса в минус показывается
  блок «Ошибки в цепочке» → «Шаг 7» (кликабельная ссылка на шаг) → «Поле «Сумма»: после
  операции и комиссии баланс становится -12 700 ₽ — денег не хватает», а плитка баланса
  получает класс `resource-negative`. Кнопка отправки заблокирована обоснованно.

### Найденные дефекты

**Д-1. Страница 404 раскрывает внутренности фреймворка.**
На полностью русском брендированном сайте `GET /no-such-page` отдаёт:

```
404
This page doesn't exist.
HTTPException: 404: Not Found
```

Английский текст плюс имя класса исключения — дефолтная страница NiceGUI.
Нужна своя страница в оформлении приложения.

## 9. Границы проведённой работы

**Не проверено: скоринг.** Закрытие приёма и расчёт CatBoost + SHAP
(`POST /admin/rounds/{id}/score`) запускает организатор. Доступ организатора не
использовался, поэтому **пик нагрузки на расчёт результатов при сотне сценариев не измерен**.
Это потенциально самая тяжёлая операция в системе и она остаётся белым пятном.

**Смещение методики.** Каждый виртуальный пользователь регистрировал **новую** учётную
запись, а `bcrypt_sha256` с дефолтной стоимостью 12 (`core/security.py:15`) — это
~250–300 мс чистого CPU на один хеш, исполняемый через `asyncio.to_thread`. В реальном
мастер-классе люди регистрируются заранее и вразнобой, а не 45 человек одновременно.
Поэтому: **фаза редактирования репрезентативна, фаза входа завышена по тяжести.**
Для чистой цифры по игровому пику прогон нужно переписать на переиспользование уже
созданных ~250 аккаунтов с нагрузкой только на редактор.

**Клиентская сторона.** Все VU исполнялись в одном Python-процессе на одной машине через
домашний канал. Клиентские CPU и сеть под контролем не находились, поэтому часть хвостовых
задержек может принадлежать генератору нагрузки. Показания «канарейки» — независимого
HTTP-клиента — этим не затронуты и служат опорой для выводов о деградации сервиса.

**Одна ошибка в ходе работы, исправлена.** На промежуточном этапе был сделан вывод, будто
интерфейс не объясняет причину заблокированной отправки при отрицательном балансе.
Вывод оказался неверным: проверялись только CSS-классы `condition-help`, `submission-ready`
и `error-box`, тогда как сообщение рендерится в блоке `scenario-corrections` /
`correction-row`. Интерфейс объясняет причину корректно и подробно, см. раздел 7.

## 10. Сырые артефакты

Находятся во временном каталоге сессии, при необходимости прогон воспроизводится:

* `report.json` — фаза 1, все замеры по шагам и показания канарейки.
* `report_play.json` — фаза 2, задержка и объём каждого клика.

Драйвер состоит из модулей: `nicegui_vu.py` — транспорт socket.io;
`uihelp.py` — обход дерева элементов и вход; `runner.py` — ступени фазы 1;
`loadplay.py` — фаза 2, управляется переменными окружения `VUS` и `CLICKS`.
