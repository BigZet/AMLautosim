## 0. Как читать

**Приоритет**

| | Значение |
|---|---|
| **P0** | Ломает сборку, запуск или выпуск. Чинить первым |
| **P1** | Реальный риск для данных, безопасности или проведения мастер-класса |
| **P2** | Заметное ограничение или долг, который скоро начнёт мешать |
| **P3** | Мелочь, чинить попутно |

**Как подтверждено**

| Метка | Значит |
|---|---|
| `измерено` | Воспроизведено запуском или замером в ходе этой проверки |
| `тест` | Подтверждено падением или прохождением тестов в этой проверке |
| `код` | Установлено чтением кода `5fc9dcc`, не воспроизводилось |
| `отчёт 20.09` | Взято из нагрузочного или релизного отчёта, в этой проверке не повторялось |

Для каждой проблемы даны варианты исправления. Вариант, помеченный ★, рекомендуется.

## 2. Выпуск и воспроизводимость

<a id="rel-01"></a>
### REL-01. Хэши текущего v10-пакета посчитаны по CRLF: чистый клон не поднимает модель · P0

**Где:** `resources/catboost_models/aml-game-organizer-settings-v1/release.json`
(`compatibility_sources`), проверка в `services/game_classifier.py:161-176`.

**Суть.** Продовый пакет закрепляет SHA-256 девяти исходников. Восемь из них посчитаны по
файлам с окончаниями строк **CRLF**, а в git они хранятся с **LF**: `game_classifier.py`,
`round_config.py`, `game_models.py`, `simulation.py`, `expanded_contract.py`,
`counterparties.py`, `semantic_contract.py`, `config/base_round.json`. Девятый
(`aml_context.py`) посчитан по LF. Пакет собирали из Windows-рабочей копии с
`core.autocrlf=true`, а в `.gitattributes` `eol=lf` задан только для четырёх inference-файлов.

**Последствие.** На любом чистом клоне (Linux-сервер, CI, `docker compose up --build` по README)
`get_game_classifier()` бросает `Classifier compatibility implementation changed`. Дальше
по цепочке `/health/ready` отвечает 503, контейнер `api` не становится healthy, а `ui`
(`depends_on: api healthy`) не запускается. Прод работает только потому, что его образ собран
на Windows (см. REL-03). Дополнительный риск: Compose монтирует `./config` с хоста поверх
образа (`docker-compose.yml:50-51`). Если на сервере обновить `config/` из git (LF), модель
отключится на живом стенде.

**Как подтверждено** (`измерено`, `тест`):
- чистый LF-чекаут `5fc9dcc`: модель не загружается; `pytest tests/unit` даёт
  **905 тестов, 99 failed + 16 errors**, из них 36 — «пакет классификатора недоступен»;
- после конвертации этих 8 файлов в CRLF пакет загружается, и все 36 падений исчезают;
- пакет `aml-game-attribute-context-unlimited-v1` не проходит проверку ни с LF, ни с CRLF:
  исходники менялись после его выпуска (см. ARCH-01).

**Варианты:**
1. ★ **Канонический хэш.** Перед SHA-256 нормализовать окончания строк
   (`data.replace(b"\r\n", b"\n")`) для текстовых файлов в `file_hash` и в скрипте упаковки;
   перевыпустить `release.json` с LF-хэшами; старую identity добавить в
   `compatible_identities`, чтобы закрепления действующих раундов не сломались.
2. Прописать `text eol=lf` для **всех** хэшируемых исходников и `config/**/*.json` в
   `.gitattributes`, выполнить `git add --renormalize .` и перепаковать. Решение хрупкое:
   первый же файл, добавленный в пакет без правки `.gitattributes`, вернёт проблему.
3. Убрать сверку исходников из рантайма. Целостность кода гарантируется сборкой образа из
   коммита в CI (REL-03, REL-06), в рантайме проверяются только артефакты модели.
   Проверка рантайма против собственных исходников от подмены кода не защищает, а
   разработчику мешает.

**Проверка исправления:** собрать образ в Linux из чистого клона → `/health/ready` = 200;
`pytest tests/unit` без падений классификатора.

<a id="rel-02"></a>
### REL-02. На Windows-чекауте legacy-исходники в CRLF, API не стартует · P0 (локально)

**Где:** рабочая копия, `services/aml_risk_model.py:110-120`, `api/main.py:24-26`.

**Суть.** Правило `eol=lf` для legacy-файлов добавили после их выписки, поэтому
`git ls-files --eol` показывает `i/lf w/crlf`. Хэш `aml_risk_model.py` не совпадает с
манифестом v8, `lifespan` падает, uvicorn не поднимается. На `master` это давало
4 падения юнит-тестов (866 passed / 4 failed).

**Варианты:**
1. ★ Разово: `git add --renormalize .` или перевыписать файлы на чистом дереве. В корне:
   вариант 1 из REL-01 (канонический хэш), тогда проблема исчезает для любых окончаний строк.
2. Инструкция для разработчиков: `core.autocrlf=input` для этого репозитория плюс проверка в CI
   `git ls-files --eol | grep w/crlf` для хэшируемых файлов.

<a id="rel-03"></a>
### REL-03. Прод невоспроизводим из git · P1

**Где:** отчёт деплоя 20.09 в `5fc9dcc:docs/verification/deploy-timeweb-2026-09-20/README.md`,
`deploy/`.

**Суть** (`отчёт 20.09`, `код`):
- релиз собран из **рабочего дерева** поверх `13e01a9`, а не из коммита;
- UI дважды обновляли **заменой файла `participant.py` в унаследованном образе**
  (`aml-runtime:20260920-amount-heading`), то есть работающий образ не соответствует ни
  одному коммиту;
- `deploy/compose.production.yml`, `backup.py`, `probe.py` существуют **только на сервере**;
- `resources/catboost_models/CURRENT.json` указывает на legacy `integration-v2-final`;
- локальный `master` отстаёт от прода на 3 коммита, поэтому ревью и нагрузочный тест
  20.09 сначала смотрели не на тот код.

**Последствие.** Невозможно ответить, какой именно код работает в бою. Откат зависит от
файлов на сервере, пересборка из git даёт другой (нерабочий, см. REL-01) результат.

**Варианты:**
1. ★ Образ собирается только в CI из тега; тег образа = SHA коммита; OCI-метки
   `org.opencontainers.image.revision`/`source`. Любое исправление = коммит + новый образ,
   патчинг файлов в образе запрещён.
2. Закоммитить `deploy/compose.production.yml` (без секретов, с `.env.production.example`),
   `backup.py` и `probe.py` в `deploy/`. Серверный каталог разворачивать из тега.
3. Отдавать версию сборки в `/health/live` (`git_sha`, `image_tag`, `model_package_sha256`)
   и выводить её в подвале админки.

<a id="rel-04"></a>
### REL-04. Старт API зависит от legacy-модели v8 · P1

**Где:** `api/main.py:24-26`, `services/model_scoring.py:22-24,61`.

**Суть.** `lifespan` всегда строит `ModelScorer` для v8 и гоняет smoke-сценарий, хотя
текущие игры — v10. Отсутствие или порча legacy-пакета роняет весь сервис.

**Варианты:**
1. ★ Загружать v8-скорер лениво, при первом v8-раунде (он уже под `lru_cache`). В
   `lifespan` проверять текущий классификатор `get_game_classifier()`.
2. В `/health/ready` показывать статус каждой модели отдельно (`current`, `legacy_v8`,
   `pinned_packages`); неготовность legacy-модели не должна давать 503.
3. Если v8-раундов в проде нет и не будет, удалить v8-путь целиком (см. ARCH-01).

<a id="rel-05"></a>
### REL-05. Исследовательский контур сломан: датасеты и модель не воспроизводятся · P1

**Где:** `scripts/aml_dataset/*`, тесты `tests/unit/test_aml_{dataset,population_*,world_graph,origins,demo_*,chain_*,…}.py`.

**Суть** (`тест`). Даже после устранения REL-01 остаются **68 failed + 11 errors**, все в
исследовательских тестах. Основные причины: `ValueError: Changed fixed financial contract`,
`No valid matched pair`, `Insufficient engine-valid chains`. Генераторы опираются на
финансовый контракт, который изменился 18–20.09 (снятые лимиты и настройки организатора).
Runtime-тестов среди упавших нет.

**Последствие.** Модель нельзя переобучить или пересобрать датасет на текущем коде.
Воспроизводимость ML держится на старых артефактах в LFS. Ни один полный прогон тестов не
зелёный, поэтому регрессии в runtime-коде тонут в шуме.

**Варианты:**
1. ★ Разделить контуры: маркеры `@pytest.mark.research` / `runtime`; обязательный CI-джоб
   только для runtime; research-джоб запускать отдельно и не блокирующим до починки.
2. Заморозить исследовательский контур на архивной версии движка: зафиксировать тег
   (например, `research-engine-2026-09-17`) и запускать генераторы из него, не из `HEAD`.
3. Обновить генераторы под новый финансовый контракт и перевыпустить датасеты. Это самый
   дорогой вариант, нужен только если планируется переобучение.
4. Вынести `scripts/aml_dataset` и LFS-датасеты в отдельный репозиторий с pinned-зависимостью
   на пакет движка.

<a id="rel-06"></a>
### REL-06. Нет CI · P1

**Где:** в репозитории нет `.github/` или аналога.

**Суть.** Все проверки, включая сотни JSON и логов в `docs/verification`, запускались вручную.
REL-01, REL-02 и REL-05 — прямое следствие: между «проверено у автора» и «работает на
чистой машине» ничего не стоит.

**Варианты:**
1. ★ Минимальный обязательный workflow: `ruff check`; `pytest -m runtime` на Linux и Windows;
   `pytest tests/api` с сервисом `postgres:16`; `git lfs pull` только для runtime-пакетов;
   проверка целостности пакетов; `docker build` и smoke `/health/ready` в собранном образе.
2. Отдельные джобы: research-тесты (REL-05), `pip-audit` (SEC-04), расширенный ruff
   (ARCH-04), ночной прогон.
3. Защита ветки `master`: merge только с зелёным CI; релизный тег собирает и публикует образ
   (REL-03).

### 3.0. Нагрузочное тестирование прода 20.09: методика, результаты, диагноз

Раздел целиком переносит данные [нагрузочного отчёта](load-test-2026-09-20.md). Цифры получены
на живом стенде `https://amlplay.ru` 20.09 и в этой проверке **не повторялись**. Проблемы и
способы исправления, вытекающие из теста, описаны ниже как PERF-01…PERF-06, SEC-02 и DATA-04.

#### Методика

- **Транспорт.** REST API снаружи недоступен (`GET https://amlplay.ru/api/v1/health/live` → 404),
  наружу открыт только NiceGUI. Поэтому нагрузка шла через настоящий транспорт интерфейса,
  socket.io поверх WebSocket, а не синтетическим HTTP-флудом.
- **Драйвер.** Headless-клиент повторяет протокол NiceGUI 3.16.0: `GET /play/register` → разбор
  дерева элементов и `listener_id` → подключение к `/_nicegui_ws/socket.io` → события
  `update:value`/`update:modelValue` + `blur` для полей и `click` для кнопок. Редирект после
  входа приходит событием `open`. Каждый виртуальный пользователь (VU) — живой клиент в памяти
  UI-процесса, как настоящий браузер.
- **Канарейка.** Независимый `GET /play/login` раз в 2 с изображает постороннего посетителя и
  показывает деградацию сервиса без влияния генератора нагрузки.
- **Фаза 1 (пассивные).** Регистрация → вход → `GET /play` → WebSocket → полный рендер →
  удержание 20–30 с. Ступени 5 → 15 → 30 → 50 VU, разгон 10 с, пауза 20 с.
- **Фаза 2 (активные).** Тот же вход, затем 8 кликов «добавить операцию» (случайный из пяти
  типов) с паузой 1,5–4 с. Измерялось время до первого ответа на клик и объём JSON.

#### Диагноз: почему отказ при CPU хоста ≤ 35%

RAM и сеть в норме, CPU хоста не выше 35%. Это указывает на фиксированные очереди, а не на
нехватку ресурсов.

| Гипотеза | Улики | Пункт |
|---|---|---|
| Пул БД по умолчанию: 5 + 10 соединений на весь API, `pool_timeout=30` | Зависания ровно «нет ответа за 30 с»; исчерпание пула даёт исключение → HTTP 500; CPU простаивает, потому что запросы стоят в очереди. `pool_pre_ping` добавляет round-trip на каждое получение соединения | PERF-01 |
| Холостой опрос, линейный по числу вкладок | `ui.timer(3)` на каждую вкладку → при 45 участниках ~15 запросов/с только опроса, каждый занимает соединение пула; `ui.timer(0.3)` → ~150 колбэков/с в event loop UI | PERF-05 |
| Один процесс API и один UI | 35% на 4 ядрах ≈ 1,4 ядра, то есть два однопоточных процесса у потолка. Агрегатный CPU хоста этого не показывает | PERF-02 |

**Проверено и исключено:**
- блокировки строк БД не сериализуют участников: запись сценария берёт `FOR SHARE` на раунд,
  `FOR UPDATE` — только команды администратора; блокировка строки пользователя персональная;
- lockout входа ни при чём: счётчик неудачных попыток персональный;
- пул httpx UI→API (`max_connections=80`, таймаут 15 с) шире пула БД и упрётся позже.

#### Как подтвердить диагноз (запускать во время повторного прогона 45 VU)

Упёрлись ли процессы в одно ядро:

```bash
docker stats --no-stream
```

Упирается ли число соединений в ~15:

```bash
docker compose exec db psql -U aml -d aml_simulator -c "SELECT state, wait_event_type, wait_event, count(*) FROM pg_stat_activity WHERE datname='aml_simulator' GROUP BY 1,2,3 ORDER BY 4 DESC;"
```

Прямая улика исчерпания пула:

```bash
docker compose logs api --since 10m | grep -iE "timeout|QueuePool|500"
```

Строка вида `QueuePool limit of size 5 overflow 10 reached, connection timed out` закрывает
вопрос.

#### Функциональный проход UI под нагрузкой

Работает корректно:
- валидация регистрации: при коротком пароле и неверном email все три ошибки полей видны

- полный игровой путь: 7 операций, цель 360 000 ₽ закрыта, диалог подтверждения,
  **отправка за 1 571 мс**, затем read-only список операций;
- автосохранение показывает «Сохранено»; при отрицательном балансе блок «Ошибки в цепочке»

#### Ограничения нагрузочного теста

- **Расчёт результатов не нагружался:** доступа организатора не было. Офлайн-замер этой
  проверки даёт ~374 мс на сценарий (PERF-06), но под конкурентной нагрузкой расчёт не мерился.
- **Фаза входа завышена по тяжести:** каждый VU регистрировал новый аккаунт, а bcrypt
  (cost 12) — это ~250–300 мс CPU на хэш. Фаза редактирования репрезентативна.
- **Генератор:** все VU работали в одном Python-процессе через домашний канал, поэтому часть
  хвостовых задержек может принадлежать генератору. Опорой для выводов служит канарейка.
- **Ошибочный промежуточный вывод исправлен:** будто UI не объясняет блокировку отправки при
  отрицательном балансе. На деле объяснение рендерится в блоке `scenario-corrections`.
- **Сырые данные** (`report.json`, `report_play.json`) и драйвер (`nicegui_vu.py`,
  `uihelp.py`, `runner.py`, `loadplay.py`) остались во временном каталоге той сессии, в
  репозитории их нет. Для повторного прогона драйвер стоит сохранить в
  `tests/load/nicegui_driver/`.

<a id="perf-01"></a>
### PERF-01. При 45 активных участниках отказ обслуживания · P1

**Где:** прод 20.09; `db/session.py:12-20`, `core/config.py:32`.

**Суть** (`отчёт 20.09`). Пассивных участников 50/50 держит без ошибок. При активном
редактировании 20 участников проходят чисто, 30 — на грани (один прогон из трёх развалился),
при 45 выполнено 145 кликов из 360, 45 отказов, HTTP 500, посторонний посетитель ждал до 18 с.
CPU хоста при этом не выше 35%. Главный подозреваемый — пул БД по умолчанию
(`pool_size=5`, `max_overflow=10`, `pool_timeout=30`). Совпадают таймауты «нет ответа за 30 с»
и 500 при исчерпании пула. **Причина серверными метриками не подтверждена.**

**Варианты:**
1. ★ Сначала подтвердить: во время прогона 45 VU снять `docker stats`, `pg_stat_activity`
   по состояниям и логи `QueuePool limit … reached`. Без этого все остальные правки — наугад.
2. Вынести параметры пула в `Settings` (`DB_POOL_SIZE`, `DB_POOL_OVERFLOW`,
   `DB_POOL_TIMEOUT`, `pool_recycle`), поставить короткий `pool_timeout` (3–5 с), чтобы
   перегрузка давала быструю ошибку и срабатывала кнопка «Повторить запрос» в UI, а не
   зависание на 30 с.
3. Снизить число запросов к БД на участника (PERF-05) и CPU на запрос (PERF-04). Это
   поднимает потолок независимо от пула.
4. Повторить прогон на 45 и 60 VU с заранее созданными аккаунтами (без bcrypt регистрации) и
   отдельно замерить общий расчёт.

<a id="perf-02"></a>
### PERF-02. API и UI работают в одном процессе каждый · P1

**Где:** `docker-compose.yml` (команды `uvicorn …` и `python -m …ui.nicegui.app` без workers).

**Суть** (`код`). Один event loop на API и один на UI. 35% CPU на 4 ядрах соответствуют
~1,4 ядра, то есть картине «два однопоточных процесса упёрлись в потолок». В API к тому же
синхронно выполняется CPU-работа (PERF-04).

**Варианты:**
1. ★ API: `--workers N` (состояния в процессе нет, сессии в БД). Учесть умножение пула:
   N × (pool_size + overflow) ≤ `max_connections` PostgreSQL (по умолчанию 100).
2. UI оставить одним процессом: NiceGUI держит дерево элементов в памяти. Снижать нагрузку на
   клиента (PERF-03, PERF-05). Горизонтальное масштабирование UI возможно только со
   sticky-сессиями на балансировщике и выносом `app.storage` в Redis; для мастер-класса это
   избыточно.
3. Вынести CPU-работу API из event loop (`asyncio.to_thread`), см. PERF-04. Это дешевле
   воркеров и помогает и с ними.

<a id="perf-03"></a>
### PERF-03. Каждая правка перестраивает всю цепочку · P1

**Где:** `ui/nicegui/participant.py:937` (`render_chain`: `chain_box.clear()` и полная перестройка).

**Суть** (`отчёт 20.09`, `код`). Ответ на один клик растёт на ~9 КБ за каждый уже
добавленный шаг: 19 КБ при одном шаге, ~80 КБ при восьми, ~160 КБ ожидается при лимите в 16.
Коммит `bfccb69` точечно обновляет только заголовок суммы; полную перестройку он не убирает.

**Варианты:**
1. ★ Карточка шага как отдельный компонент, у которого есть `update(step)`. Мутация (добавить,
   удалить, копировать, переставить) обновляет только затронутые карточки и сводку;
   перестановка — `move()` элементов, а не пересоздание.
2. Промежуточный шаг: сворачивать неактивные карточки в лёгкое «резюме» (одна строка) и
   раскрывать полную форму только у редактируемого шага. Это сильно режет payload без
   переписывания логики.
3. Критерий приёмки: при цепочке из 8 шагов ответ на клик ≤ 25 КБ; регрессии гонок
   autosave, перестановки и навигации по ошибкам проходят.

<a id="perf-04"></a>
### PERF-04. Предпросмотр и сохранение канонизируют цепочку 6 раз, синхронно в event loop · P1

**Где:** `services/scenarios.py:46-65` → `scenario_service.prepare_scenario` →
`counterparties.canonical_expanded_steps` → `aml_context.canonical_steps` →
`semantic_contract.canonical_steps` → снова `canonical_expanded_steps` (v8) и т. д.

**Суть** (`измерено`, профиль на цепочке из 9 шагов):

| Метрика на один предпросмотр | Значение |
|---|---|
| Время CPU | **8,4 мс** |
| Вызовов `canonical_expanded_steps` | 6 |
| Вызовов `validate_config` (v9 + v10) | 14 |
| Вызовов `deepcopy` | ~12 500 |

v10 реализован поверх v9, тот поверх v8, и каждый слой заново валидирует конфиг раунда и
заново канонизирует шаги. Всё это идёт **синхронно внутри async-обработчика**, поэтому
блокирует event loop API. UI после каждой правки делает предпросмотр (через 0,4 с) и
сохранение (через 1 с), каждый вызов проходит этот путь целиком: ~17 мс блокировки на правку
при 9 шагах и больше при 16.

**Варианты:**
1. ★ Канонизировать один раз: `canonical_round_steps` возвращает результат, а
   `build_snapshot`/`evaluate` принимают уже канонические шаги, без повторного
   `canonical_steps` внутри. Валидированный `BehaviorV10`/`AMLContext` кешировать по
   `config_version` раунда: конфиг неизменяем после старта.
2. Выполнять `prepare_scenario` через `asyncio.to_thread`: event loop перестаёт блокироваться,
   хотя CPU остаётся тем же.
3. Объединить предпросмотр и сохранение: `PUT /scenario` уже считает snapshot и может вернуть
   `blockers`, тогда отдельный `POST /preview` нужен только при несохранённой цепочке.

<a id="perf-05"></a>
### PERF-05. Холостой опрос · P2

**Где:** `ui/nicegui/app.py:340` (`ui.timer(3, screen.poll)`), `participant.py:647`
(`ui.timer(0.3, self.tick)`), `participant.py:649-672` (лидерборд).

**Суть** (`измерено`, `код`):
- каждая вкладка раз в 3 с запрашивает `/rounds/current/state`; ответ включает полный
  `game_config` (**~18,5 КБ**, разбор pydantic ~0,7 мс), хотя во время игры он не меняется.
  45 вкладок дают ~15 запросов в секунду, и каждый занимает соединение пула (PERF-01);
- после расчёта каждая вкладка раз в 3 с запрашивает лидерборд `limit=200`, делает
  `board.clear()` и перестраивает таблицу. Это происходит ровно тогда, когда вся аудитория
  смотрит результаты;
- у организатора опрос лёгкий (только текущий раунд), но и он раз в 3 с получает полный конфиг.

**Варианты:**
1. ★ Толкать изменения, а не опрашивать. UI — один процесс, поэтому команда организатора
   (старт, расчёт, перезапуск), проходящая через тот же NiceGUI-процесс, может сразу
   оповестить всех подключённых участников (реестр клиентов → `poll()` у каждого). Фоновый
   опрос оставить редким, раз в 20–30 с, как страховку.
2. Лёгкий эндпоинт статуса: `GET /rounds/current/status` → `{round_id, status,
   config_version, scenario_revision}`. Полное состояние и конфиг запрашивать, только когда
   что-то из этого изменилось (либо ETag/`If-None-Match`).
3. Лидерборд загружать один раз при переходе в `completed` и по кнопке «Обновить»;
   перерисовывать только при изменении хэша ответа.

### PERF-06. Расчёт последовательный, потолок ~300 участников · P2

**Где:** `services/scoring_service.py` (цикл по сценариям), `game_classifier.py:225-238`,
`ui/nicegui/organizer.py:519` (таймаут 120 с).

**Суть** (`измерено`). `predict` с SHAP по трём окнам занимает **~374 мс на сценарий**
(на сервере 20.09 медиана 340 мс). Сценарии считаются по очереди в одной транзакции под
блокировкой раунда: 50 участников ≈ 19 с, 300 ≈ 110 с. После 120 с UI организатора получает
таймаут, хотя расчёт на сервере продолжается. Прогресса расчёта не видно.

**Варианты:**
1. ★ Параллелить расчёт: CatBoost вызывается с `thread_count=1`, поэтому можно считать
   несколько сценариев одновременно через `ThreadPoolExecutor` на 2–4 потока с последующей
   записью в той же транзакции.
2. Фоновая задача: `POST /score` сразу возвращает 202 и переводит раунд в `scoring`, прогресс
   хранится в `scoring_summary` (`done/total`), UI показывает прогресс-бар. Таймаут UI
   перестаёт быть ограничением.
3. Считать SHAP лениво: вероятность — для всех, полное объяснение — при первом открытии
   результата участником. Экономит основную часть времени, но усложняет модель данных.

<a id="data-02"></a>
### DATA-02. Закрытие приёма удаляет черновики · P2

**Где:** `services/scoring_run.py:45-49`, диалог `ui/nicegui/organizer.py:502`.

**Суть** (`код`). При переходе `active → closed` удаляются все сценарии в статусе `editing`.
Организатор получает общее предупреждение «Все неотправленные черновики будут удалены», но
не видит, **сколько** их. Участников о приближающемся закрытии не предупреждают.
Число удалённых не попадает ни в аудит, ни в `scoring_summary`. Участник, не нажавший

## 5. Безопасность

<a id="sec-01"></a>
### SEC-01. Нет ограничения частоты входа и регистрации · P1

**Где:** `services/authentication.py:49, 84-119`; периметр.

**Суть** (`код`):
- регистрация открыта и ничем не ограничена: скрипт заводит тысячи аккаунтов, которые
  попадают в список организатора (DATA-04);
- lockout работает только по аккаунту; перебор одного пароля по многим email не ограничен.
  По IP на API ограничить нельзя, потому что все запросы идут от UI-процесса;
- ответ `429 login_temporarily_locked` (`:97-102`) приходит **до** проверки пароля и только
  для существующего email. Это перечисление аккаунтов, к тому же быстрее по времени;
- 10 неверных паролей на известный email блокируют чужой аккаунт на 5 минут. На
  мастер-классе, где соседи знают email друг друга, так можно выключить конкурента.

**Варианты:**
1. ★ Ограничение частоты в UI-процессе: он видит IP клиента (`X-Forwarded-For` от
   балансировщика, доверять только адресам балансировщика). Токен-бакет по IP для входа и
   регистрации, например 10 попыток в минуту.
2. Выровнять ответы: при lockout тоже вызывать `verify_password` с фиктивным хэшем и отвечать
   тем же 401 `invalid_credentials`, а сообщение о блокировке показывать только после
   правильного пароля. Lockout считать по паре (email, IP), а не только по email.
3. Код приглашения раунда (или общий код мастер-класса) при регистрации отсекает посторонних
   и массовую регистрацию.

<a id="sec-02"></a>
### SEC-02. Периметр: открытый 8080, нет защитных заголовков, стандартная 404 · P1

**Где:** прод (балансировщик Timeweb → HTTP 8080), `docker-compose.yml:84`
(`"${UI_PORT:-8080}:8080"` на всех интерфейсах), `deploy/nicegui.nginx.conf`.

**Суть** (`отчёт 20.09`):
- порт 8080 опубликован на всех интерфейсах, доступ ограничен не только балансировщиком:
  к UI можно обратиться напрямую по HTTP, в обход HTTPS;
- nginx-конфиг из репозитория в проде не используется: балансировщик идёт прямо в NiceGUI.
  Значит, нет HSTS, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`,
  `Referrer-Policy`;
- `GET /no-such-page` отдаёт английскую страницу NiceGUI с `HTTPException: 404: Not Found`.

**Варианты:**
1. ★ Firewall на сервере: 8080 принимает только адреса балансировщика; в Compose публиковать
   `127.0.0.1:8080` или адрес внутренней сети.
2. Заголовки ставить в самом приложении (middleware Starlette в NiceGUI-приложении): это
   работает при любом периметре. HSTS — только при HTTPS.
3. Своя 404: `app.add_exception_handler(404, …)` или `@ui.page` для неизвестных путей с
   русским текстом в оформлении игры и ссылкой на `/play`.

<a id="sec-03"></a>
### SEC-03. `passlib` не поддерживается, `bcrypt` закреплён на 3.2.2 · P2

**Где:** `requirements.in`, `core/security.py:15`.

**Суть** (`код`). `passlib` 1.7.4 не обновлялся с 2020 года и плохо совместим с новыми
версиями `bcrypt`, поэтому `bcrypt` закреплён на 3.2.2 (2021). Каждое обновление окружения —
риск сломать вход. Хэши хранятся в формате passlib `$bcrypt-sha256$v=2,…`, который другие
библиотеки напрямую не читают.

**Варианты:**
1. ★ Двухэтапная миграция: новые хэши — Argon2id через `pwdlib` (или `argon2-cffi`);
   `passlib` оставить только для проверки старых `$bcrypt-sha256$` хэшей и перехэшировать
   пароль при успешном входе. Когда старых хэшей не останется (или по истечении срока с
   принудительным сбросом пароля), убрать `passlib`.
2. Реализовать проверку формата `bcrypt_sha256 v2` самостоятельно поверх `bcrypt`
   (HMAC-SHA256 от пароля с солью, затем bcrypt; ~20 строк). Покрыть тестом на реальных
   хэшах из текущей БД. Данные мигрировать не нужно, но это своя криптографическая обвязка,
   которую придётся поддерживать.

### SEC-04. Статус уязвимостей зависимостей неизвестен с 16.09 · P2

установлен в окружении и не запускался.

**Варианты:**
1. ★ `pip-audit -r requirements.txt` в CI (REL-06) плюс еженедельный запуск.
2. Dependabot или Renovate для `requirements*.txt` и базового образа `python:3.13-slim`,
   `postgres:16`.

### SEC-05. Мелкие пункты · P3

## Приложение A. Методика и воспроизведение

Проверка шла на отдельном worktree `5fc9dcc` с `core.autocrlf=false`, так что все файлы
выписаны ровно как в git. Использовалось окружение `.venv` проекта (Python 3.13).

```bash
git worktree add --detach <path> origin/master
git lfs checkout
pytest -q tests/unit --junitxml=unit.xml
```

Эксперимент для REL-01: 8 compatibility-исходников переведены в CRLF (`aml_context.py`
оставлен в LF), после чего повторно запущены 26 файлов с падениями. Проверку хэшей можно
повторить так: для каждого пути из `release.json → compatibility_sources` сравнить SHA-256
файла как есть, с `\r\n → \n` и с `\n → \r\n`.
