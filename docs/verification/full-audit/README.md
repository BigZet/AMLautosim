## Подтверждённые находки

### A-01 — P1: штатный запуск pytest не собирает весь набор

Команда `python -m pytest tests -q -p no:cacheprovider` в Python 3.13 образе
aml-catboost:v1 остановилась на пяти import-file-mismatch: одноимённые
`test_contract_versions`, `test_counterparties`, `test_operation_timeline`,
`test_profile_history`, `test_purchases` находятся в unit и api. В pytest.ini
не выбран importlib-режим. Нельзя считать такую команду полноценной зелёной проверкой.
Для продолжения аудита выполнен тот же набор с `--import-mode=importlib`; исправления
конфигурации тестов пока не делались. Логи: .local-run/full-audit/pytest.log и pytest-importlib.log.

### A-02 — P2: форма предлагает редактировать неподдерживаемые параметры модели

В чистом раунде 1 изменить начальный баланс с 180000 на 180001 и нажать
«Сохранить настройки». Поле редактируется, но сервер отвечает «Конфигурация не
поддерживается моделью CatBoost». Пользователь заранее не видит, что параметр
фиксирован. Аналогичные элементы стоимости/лимитов и доступности карточек остаются
в форме. Серверный запрет корректен; проблема — вводящий в заблуждение интерфейс.
«Загрузить актуальные» с подтверждением восстанавливает сохранённые значения.

### A-03 — P2: ошибки конфигурации раскрывают пользователю внутренние схемы

В предыстории заменить дату первого события 2026-08-15 на 2026-09-15 при начале
раунда 2026-09-14, сохранить. Запрет будущей истории корректен, но сообщение содержит
`function-after[_has_operations(), GameConfigIn]`, «Input should be 7»,
«Extra inputs are not permitted», `ExpandedGameConfigIn`. Это не понятная ошибка
конкретного поля и ошибочно упоминает снятый с эксплуатации v7. После исправления
даты сохранение проходит.

### A-04 — P2: статус общего плана противоречит таблице этапов

Первая строка docs/plans/aml-behavior/README.md говорит «этап 08 не начат»,
в таблице того же документа этап завершён. Документы совместимости ещё описывают
обязательное обслуживание старых раундов, хотя новый утверждённый выпуск начинается
с чистой БД. Исторические критерии нужно отличить от критериев текущего выпуска.

### A-05 — P3: таблица результатов организатора не показывает числовой риск

Нативный Chrome, стенд 58309, завершённый раунд 3: колонки «Баллы», «Скрытность»,
«Ресурсы», «Риск». В колонке риска только «Подозрительно», числовой риск отсутствует;
булево поле блокировки показывается как `false`. Это затрудняет проверку результата.
Категория при риске около 45 соответствует сохранённым старым порогам, поэтому сама
по себе не объявляется дефектом расчёта; пригодность порогов для учебной рубрики
требует отдельного продуктового решения.

## Журнал интерактивной проверки

Используется нативный Google Chrome через CUA: доступного браузерного расширения
в сессии нет. Пароли в менеджер браузера не сохраняются.

- 58309: вход организатора, просмотр результата и колонки риска, переход на «Об игре».
- 58409: вход в чистый раунд, осмотр профиля/истории/ресурсов/карточек.
- Изменение баланса на +1 → отказ, восстановление сохранённых настроек → успешно.
- Будущее историческое событие → отказ, исправление и сохранение → успешно.
- Раскрыт каталог, добавлена сторона. Попытка ввода кириллицы через native typeText не была проверена перед сохранением; в БД оказалось имя из одного пробела. Потерю кириллицы не приписываем приложению без отдельного воспроизведения. Принятие пробельного имени подтверждено БД и пустым пунктом выбора участника.
- В каталоге поля «Категория организации» доступны даже физическим лицам,
  значения работодателя/магазина показаны как employer/groceries; отмечено для UX-разбора.

### A-06 — P2: имя стороны из пробела принимается и создаёт пустой пункт

В аудиторском раунде сохранена сторона kind=person, name=" ". Сервер разрешил
сохранение и старт; выбор отправителя показывает пустую пятую строку. Подтверждено
прямым чтением снимка из изолированной БД. Нужны trim и запрет пустого после trim
имени. Это отдельный дефект валидации; происхождение пробела при нативном вводе
не является доказанным дефектом приложения.

### A-07 — P2: до первой операции участнику не показаны цель и стартовые ресурсы

После входа в активный пустой раунд видны профиль, каталог и фраза «Ресурсы будут
рассчитаны после проверки цепочки». Ни цель 400000, ни баланс/энергия/время не видны.
После добавления операции они появляются, но при незаполненном отправителе снова
заменяются общей ошибкой. Начальные условия нужны ещё до выбора первой карточки.

### A-08 — P3: незаполненная новая карточка выглядит как ошибка запроса

Добавить входящий перевод, пока не выбрать отправителя, дождаться автопроверки.
Показаны красная ошибка, «Есть несохранённые изменения» и «Повторить запрос».
Это ожидаемая стадия заполнения формы, не сбой сети. Следует различать неполный
черновик и ошибку сохранения, сохраняя понятные условия задания.

### A-09 — P1: значительная часть regression-suite не проверяет новый выпуск

Основные причины падений: chain-фикстура не выбирает sender_id/recipient_id;
ожидания v7/default-четырёх карточек; старые метаданные; прямое внедрение
неподдерживаемых снимков; DTO с risk_model в редактируемой конфигурации; вызовы
нового scorer без закреплённой модели. Падения нельзя просто отключить:
нужны новые v8-фикстуры и перенос сохранённых проверок авторизации, ревизий,
гонок и UI на текущий контракт. 4 успешно перенесённые аудиторские проверки
не заменяют весь оставшийся набор.

### A-10 — P2: старый «Базовый риск» остался в переопределениях карточек

Статически подтверждено: ConfigForm.operations перебирает все metadata.overrides;
editor_metadata включает risk_weight с подписью «Базовый риск». Убрана общая
панель скоринга, но вложенный старый регулятор остаётся. Реального влияния на
CatBoost не имеет; изменение отклоняется как несовместимость. Нужна очистка
этих элементов вместе с неподдерживаемыми затратами, без удаления нужных затрат
из совместимого снимка.

## Завершение интерактивного прохода

- Две выдачи наличных 100000 + 21000: черновик сохранился, финальная отправка
  заблокирована, показан лимит 120000. Списания 122000 включают покупку 1000,
  целевой оборот 121000, комиссия 1210. Это ожидаемое разделение черновика и допуска.
- Полная допустимая 10-шаговая цепочка подготовлена через API из demo_steps(purchase),

  конфликт: локально очищенная покупка сохранена в редакторе при серверном изменении
  на 1200; явная загрузка серверной версии восстановила 1200 и допустимость отправки.
- Отмена диалога отправки сохранила редактирование; подтверждение перевело в ожидание.
  До общего расчёта ни риска, ни SHAP участнику не показано.
- Блокировка второго тестового участника через UI с причиной: вход 403 account_blocked.
  Поиск по email, разблокировка с причиной, журнал обеих операций проверены. После
  разблокировки новый вход успешен. Этот участник не получил чужого результата.
- Организатор запустил общий расчёт с подтверждением. Результат появился у участника
  автоматически: риск **45,02**, итог **46,14**, ресурсы **29,73**, место 1.
- В SHAP 84 фактора, база **58,322882**, исходный прогноз **45,019524**, ограничение 0,
  поправка округления **+0,000476**, итог **45,02**. Проверены оба направления вкладов.
- Нативный Chrome, эмуляция **390×844**: краткое объяснение и длинные названия
  визуально помещаются по ширине; подробный расчёт раскрыт и свёрнут касанием.

## Дополнительные замечания к выпуску

### A-11 — P2: комплект документации и исходников ещё не оформлен как воспроизводимый релиз

Рабочий каталог содержит множество изменённых и неотслеживаемых файлов, включая
новый модельный пакет. Локальный Docker build использует их, но чистый checkout
текущего commit не гарантирует тот же комплект. Перед деплоем нужно выбрать состав
релиза, сохранить исходники/итоговую модель и manifest; большие датасеты и эксперименты
оставить отдельными артефактами. Не следует автоматически добавлять весь каталог.
В MODEL_CARD итогового пакета ещё написано «В API игры не подключена» — это статус
момента обучения, не текущего приложения; неизменяемый пакет нельзя править без
учёта контрольных сумм, актуальный статус следует явно дать в документации выпуска.

### A-12 — P3: мелкие несогласованности интерфейса

Категории организаций employer/groceries не переведены, поле категории показано
физическим лицам; SHAP использует десятичную точку, тогда как итог — запятую.
Кнопки копирования/удаления карточек представлены иконками без понятного имени в
наблюдавшемся accessibility-дереве. Нужны проверка доступности и единое форматирование.
Отсутствие удаления новой стороны в просмотренной форме — вопрос UX, не подтверждённое
нарушение контракта. Цвет/порог категории риска около 45 — отдельное продуктовое решение.
