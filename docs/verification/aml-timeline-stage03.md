# Этап 03: временная шкала операций

Дата: 13 сентября 2026 года. Статус: критерии этапа 03 выполнены.
Рабочая копия: база `be4cb32`, изменения не закоммичены.

## Реализованное поведение

В контракте v8 действует `operation-timeline-v1`. Версия хранится в блоке
`behavior.timeline`; для ранее созданных тестовых снимков v8 без этого поля
используется v1. V7 сохраняет прежний движок и формат результата.

- Первый шаг происходит в `starts_at`, его канонический `interval_minutes` равен `null`, ожидание бесплатно.
- Для остальных шагов доступны 1, 10, 60, 1440 минут, с расходом 0, 1, 2, 4 единиц игрового времени. Пропуск/null после первого шага нормализуется в 1 минуту.
- Интервал относится к шагу; при переносе на первое место сбрасывается. Бывший первый шаг получает 1 минуту. Удаление/вставка/перестановка пересчитывают всю шкалу.
- Накопление выполняется в UTC как фактически прошедшие минуты, отображение — в часовом поясе снимка. Переходы летнего/зимнего времени не изменяют длительность ожидания; «сутки» означают 1440 минут.
- Ночь: 00:00–05:59, день: 06:00–17:59, вечер: 18:00–23:59. Время суток вычисляется для каждой операции, включая первую.
- Календарь не сдвигается на базовую стоимость карточки: игровые единицы времени и реальные минуты — разные величины. Начало сценария и календарные моменты не зависят от часов сервера.

Формула расхода времени v8:

```text
время операции = max(минимум,
  базовая стоимость карточки + поправка суммы + стоимость канала + параметры операции)
полный расход = время операции + стоимость ожидания
```

Старый `velocity_time` не участвует даже у первого шага. Тест дополнительно
заменяет все старые надбавки на 999 и проверяет неизменность результата v8.
Денежные комиссии, энергия, лимиты карточек и проверка нехватки ресурсов
используют общий расчётный модуль; золотые примеры v7 проходят без изменений.

## Данные, API и интерфейс

Шаг хранит только выбранный интервал. `occurred_at`, `elapsed_minutes`, `pace`,
стоимость ожидания и ручные `context.time_of_day`/`context.velocity` во входе
отклоняются. Интервал принимает только допустимое целое число, не bool, строку
или дробное значение.

Результат v8 имеет `schema_version=6`, `ruleset_version=expanded-rules-stage03-v1`
и отдельный блок `timeline`: версия, часовой пояс, список моментов операций,
интервалов, времени суток, темпа и раздельных затрат операции/ожидания.
`per_step.time_cost` содержит их сумму. В результате v7 новый блок отсутствует.

Редактор показывает календарный момент и выбор ожидания только после первого
шага. Сводка ресурсов и административный просмотр показывают календарь отдельно
от игрового остатка. При изменениях используются те же чистые функции времени,
что и на сервере; результат API содержит повторно вычисленные значения.

## Временный детерминированный скоринг

Для внутреннего сравнения добавлен `expanded-scoring-stage03-v1`:

- Первый шаг не получает фактор темпа.
- 1 минута соответствует `rapid`, 10 — `normal`, 60/1440 — `spaced`; численные вклады берутся из снимка текущих правил скоринга.
- Фактор быстрого перехода credit→debit учитывается только при интервале 1 минута и выполнении прежнего условия доли суммы. Простое соседство через сутки не считается быстрым переходом.
- Время суток берётся из шкалы; ручные характеристики получателя/отправителя не восстанавливаются из старых значений по умолчанию.

Это временный игровой сравнительный расчёт, не утверждённая AML-рубрика и не
разметка датасета. Обучение CatBoost и совместная оценка новых эталонов не выполнялись.

## Граница доступности и проверки

Запуск v8 в обычной игре всё ещё запрещён до этапа 06. В API-тесте временно
подменяются только проверки доступности в `prepare_scenario` и окончательной
отправке. Нормализация, ресурсный расчёт, preview/save/submit, повтор команды,
HTTP и PostgreSQL выполняются настоящим кодом. Проверки старта и скоринга не
подменяются; отдельно подтверждён отказ внешнего preview v8 без тестовых подмен.

Окружение: macOS, Python 3.12.14 из `.venv`, отдельный одноразовый `postgres:16`
`aml-timeline-stage03-test`, loopback-порт 62872. API-команды используют
`TEST_ADMIN_DATABASE_URL` этой БД; каждый прогон создаёт и удаляет свою базу

## Браузерный проход

```bash
.venv/bin/python -m scripts.preview_operation_timeline
```

Адрес: `http://127.0.0.1:58184/first`. Стенд использует реальные компоненты
редактора и расчёт ресурсов этапа 03, но транспорт в памяти; не включает обычную
игру и не подключает БД. Перезапуск стенда удаляет его тестовые цепочки.

В Safari через UI automation выполнен сценарий:

1. Начало 13.09.2026 23:30 Europe/Moscow; поступление, перевод, снятие; осталось 26 единиц времени.
2. Перед переводом выбран час: второй шаг 14.09 00:30, третий 00:31; осталось 24.
3. Перед снятием выбраны сутки: третий шаг 15.09 00:30; осталось 20. Раздельные затраты ожидания 0/2/4 видны в сводке.
4. Первый шаг перемещён вниз: перевод становится первым без ожидания; поступление через минуту; снятие 14.09 23:31; осталось 22.
5. Средний шаг удалён: перевод 13.09 23:30, снятие 14.09 23:30; осталось 24.
6. После reload обе даты, интервал суток и остаток 24 восстановились. Такой же порядок действий проверен автоматическим тестом редактора.
