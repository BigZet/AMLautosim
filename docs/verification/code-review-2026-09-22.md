**Дата:** 2026-09-22
**Ветка:** `master` @ `b441e04`
**Объём:** runtime-код `src/` (~16,8 тыс. строк), `deploy/`, `docker-compose.yml`, выборочно `scripts/` и `tests/`.

## 1. P0 — ломает запуск

### 1.1 API не стартует на Windows-чекауте из-за CRLF в файлах, покрытых контрольными суммами

**Факт.** `pytest tests/unit` падает на первом же тесте с моделью:

```
FAILED tests/unit/test_aml_backend_dispatch.py::test_dispatch_rejects_v9_and_missing_classifier
ValueError: Inference source version mismatch: aml_risk_model.py
```

`git ls-files --eol` показывает, что в индексе LF, а в рабочей копии CRLF:

```
i/lf    w/crlf  attr/text eol=lf   src/aml_workshop_simulator/services/aml_risk_model.py
i/lf    w/crlf  attr/text eol=lf   src/aml_workshop_simulator/services/aml_dataset_features_v3.py
```

Полный прогон `pytest tests/unit`: **866 passed, 4 failed, 1 skipped** (7 мин 26 с).
Все четыре падения вызваны одной причиной: три дают `Inference source version mismatch`,
а `test_semantic_v9.py::test_pinned_v8_source_files_unchanged` видит несовпадение
SHA-256 закреплённых исходников v8.

`.gitattributes` требует `eol=lf`, но правило добавили уже после того, как файлы были
выписаны с `core.autocrlf=true`. Git не перезаписывает рабочую копию сам, поэтому хэш
исходника (`aml_risk_model.py:110-120`) не совпадает с манифестом.

**Последствие.** `lifespan` вызывает `get_model_scorer()` (`api/main.py:26`), конструктор
бросает `ValueError`, и **uvicorn не поднимается вообще**, хотя в текущем контракте v10
эта модель не участвует. Локальный запуск по README на Windows не работает.

**Исправить сейчас:**

```bash
git add --renormalize . && git status
```

или `git rm --cached -r . && git reset --hard` (только на чистом дереве).

**Исправить в корне:** считать хэш исходников после нормализации окончаний строк
(`data.replace(b"\r\n", b"\n")`) либо проверять целостность исходников только в CI и
при упаковке релиза, а не при каждом старте. Проверка рантайма против собственных
исходников бьёт по разработчику, но от подмены кода не защищает: тот, кто может поменять
`.py`, поменяет и проверку.

### 1.2 Старт API зависит от legacy-модели v8

`api/main.py:24-26` при каждом запуске строит `ModelScorer` для контракта v8
(`integration-v2-final`) и прогоняет smoke-сценарий. Текущие игры — v10, и их
классификатор проверяется отдельно в `/health/ready`.

Итого legacy-пакет — обязательная зависимость старта. Если его убрать из образа
(`deploy/Dockerfile` копирует пять пакетов моделей) или у него разойдётся хэш, лежит весь
сервис, включая v10-игры.

**Предложение:** грузить v8-скорер лениво (он и так под `lru_cache`) или только при наличии
v8-раундов. В `lifespan` проверять текущую модель v10 через `get_game_classifier()`.
В `/health/ready` отдавать статус каждой модели отдельно.

## 2. P1 — данные, безопасность, надёжность

### 2.1 Перезапуск игры удаляет весь журнал аудита

`services/admin_rounds.py:197`:

```python
await db.execute(delete(AuditEvent))
```

Модуль `services/audit.py` описан как «Append-only audit trail», но при перезапуске
удаляются все события без фильтра: `participant_blocked`/`participant_unblocked` с
причинами, `scoring_failed`, `round_scored`. Остаётся только новое `round_created`,
причём события «кто и когда перезапустил» нет вообще.

**Предложение:**
- не удалять аудит: у события есть `round_id`, старый раунд можно просто перестать показывать;
- если нужна очистка, удалять только события игры (`round_id = old_id`) и писать
  `round_restarted` с `previous_round_id` и сводкой удалённого;
- события про учётные записи (`participant_*`) хранить всегда: блокировка глобальная и
  переживает раунд. Сейчас её причина исчезает, а сама блокировка остаётся.

### 2.2 Закрытие приёма молча удаляет черновики

`services/scoring_run.py:45-49` при переходе `active → closed` делает
`DELETE FROM scenarios WHERE status = 'editing'`. Участник, который не успел нажать
«Отправить», теряет цепочку без следа: ни события аудита, ни числа удалённых в
`scoring_summary`, ни предупреждения организатору.

**Предложение:** хотя бы записать число удалённых черновиков в событие `round_closed`.
Лучше — переводить их в статус `abandoned` вместо удаления и перед расчётом показывать
организатору в UI, сколько участников не отправили сценарий.

### 2.3 Проверка целостности модели хэширует мегабайты при каждом вызове, блокируя event loop

`GameClassifier.verify_integrity()` (`services/game_classifier.py:162-173`) читает и
хэширует SHA-256 все файлы пакета (`model.cbm` ~6 МБ) и исходники экстрактора. Вызывается:

- в `get_game_classifier()` при **каждом** вызове (`:289`);
- в `check_config()` при **каждом** вызове (`:179`), то есть дважды на каждый сценарий при
  расчёте: `score → predict → check_config` плюс `scorer.check_config` в `scoring_service`;
- в `/health/ready` через `get_game_classifier()`, а Compose дёргает healthcheck раз в 10 с;
- в `require_new_round_allowed`, `game_config()` и в админском `GET /game-config/default`.

`/health/ready`, `game_config()` и `prepare_config()` выполняются **синхронно прямо в
event loop** API. Расчёт выполняется в `asyncio.to_thread`, но при 50 сценариях получается
~100 хэширований по 6 МБ.

**Предложение:** проверять целостность один раз при загрузке пакета (в `__init__` это уже
делается). Если нужна защита от подмены файла на ходу, сравнивать `mtime`/`size` и
пересчитывать хэш только при изменении. Синхронные тяжёлые вызовы в async-обработчиках
обернуть в `asyncio.to_thread`.

### 2.4 Вход и регистрация: нет ограничения частоты, lockout раскрывает аккаунт

- **Регистрация открыта и ничем не ограничена** (`services/authentication.py:49`): ни
  лимита, ни капчи, ни кода приглашения. Скрипт заливает таблицу `users` тысячами
  аккаунтов, и все они видны в админском списке участников.
- **Lockout только по аккаунту** (`:110-116`). Перебор одного пароля по многим email не
  ограничен ничем. Ограничить по IP на API нельзя: все запросы идут от UI-процесса, а NiceGUI
  не передаёт IP клиента. В nginx нет `limit_req`.
- **Перечисление аккаунтов:** для заблокированного аккаунта ответ `429
  login_temporarily_locked` приходит *до* проверки пароля (`:97-102`), а для несуществующего
  email такого ответа не бывает. Десять неверных попыток подряд показывают, существует ли
  адрес. Ответ ещё и быстрее, потому что bcrypt не вызывается.
- **Можно заблокировать чужой аккаунт:** десять неверных паролей на известный email
  выкидывают участника на 5 минут. На мастер-классе, где email соседей видно, это реально.

**Предложение:** `limit_req_zone` в nginx для `/play/login`, `/play/register`,
`/admin/login` (или счётчик по IP в UI-процессе); для lockout-ответа тоже вызывать
`verify_password` с фиктивным хэшем и выровнять ответ; при необходимости добавить код
приглашения раунда при регистрации.

### 2.5 Лидерборд перезапрашивается и перерисовывается каждые 3 с

`ParticipantScreen.poll` (`ui/nicegui/participant.py:558-582`): после завершения раунда
каждая открытая вкладка раз в 3 с делает `GET /leaderboard?limit=200`, а затем
`self.board.clear()` и заново строит `ui.table`.

После `completed` лидерборд меняется только при блокировке участника. При 50 вкладках это
~17 запросов в секунду с оконной функцией `dense_rank` по всем результатам плюс рассылка
таблицы по WebSocket. И всё это в момент, когда вся аудитория одновременно смотрит
результаты.

**Предложение:** загружать один раз при переходе в `completed` и по кнопке «Обновить»;
перерисовывать, только если изменился хэш ответа. Дополняет п. 6.3 нагрузочного отчёта.

### 2.6 Сессии копятся бесконечно

Сессия создаётся на каждый вход (`authentication.py:142-150`), отзывается при выходе, но
удаляется только каскадом при удалении пользователя. Ни задачи очистки, ни `DELETE` по
`expires_at` нет. Индекс `ix_sessions_expires_at` существует, но не используется.

**Предложение:** при старте API и/или раз в час удалять
`expires_at < now() - interval '7 days' OR revoked_at < now() - interval '7 days'`.

### 2.7 Нет CI

Каталога `.github/` нет. Раз проверки существуют в виде отчётов в `docs/verification/*.json`
и `*.log`, их запускали вручную. Пункт 1.1 как раз показывает, что между «проверено» и
«работает у следующего разработчика» ничего не стоит.

**Минимальный workflow:** `ruff check`, `pytest tests/unit` на Linux и Windows,
`pytest tests/api` с сервисом `postgres:16`, `git lfs pull` и проверка хэшей пакетов
моделей, `docker build`.

### 2.8 Мелкое по безопасности и эксплуатации

- `COOKIE_SECURE=false` по умолчанию, а прод работает по HTTPS (`amlplay.ru`). В
  `deploy/README.md` и `.env.example` надо явно требовать `true` для прода.
- `/api/v1/rounds/current` и `/api/v1/rounds/{id}/cards` доступны без сессии
  (`api/routers/rounds.py:27-42`). Наружу nginx их закрывает, но на уровне API это
  неочевидная граница. Если так задумано, стоит комментарий.
- `X-Request-ID` принимается от клиента как есть (`api/main.py:65-72`) и попадает в аудит.
  Для корреляции это удобно, но через UI клиент задать его не может, поэтому доверять
  заголовку извне нет смысла.
- `health_ready` проглатывает любые исключения БД (`api/routers/health.py:65,76`) и не
  пишет их в лог. При 503 причину не узнать.

## 3. P2 — качество кода и сопровождаемость

### 3.1 Пути и конфигурация

- `services/model_scoring.py:21-24, 45`: `Path("resources/...")`, `Path("config/model/...")`
  относительны к CWD. В `game_classifier.py` уже есть правильный `ROOT = Path(__file__).parents[3]`,
  стоит использовать его везде.
- Модели выбираются через две разные переменные: `AML_MODEL_PATH` (v8, нигде не
  задокументирована) и `AML_PROBABILITY_MODEL_PATH` (v10, задана в Compose). Обе стоит
  вынести в `core/config.py::Settings`, как остальную конфигурацию.
- UI читает `os.environ` напрямую (`ui/nicegui/app.py`), без валидации: `UI_PORT=abc`
  падает с невнятным `ValueError`. Стоит сделать отдельный `UISettings(BaseSettings)`.
- Параметры пула БД, см. нагрузочный отчёт §6.1.

### 3.2 HTTP-семантика и API

- `GET /admin/game-config/default?schema_version=9` сначала вычисляет конфиг, потом
  отвечает `409 Conflict` (`api/routers/admin/rounds.py:36-42`). Для неподдерживаемого
  значения параметра правильнее 422, а надёжнее всего `Literal[8, 10]` в сигнатуре. То же
  в `restart` (`services/admin_rounds.py:190`), там проверка стоит *после* взятия advisory lock.
- `list_participants`: `ilike(f"%{query}%")` без экранирования, поэтому `_` и `%` из ввода
  работают как шаблоны (`services/participants.py:76-79`). Есть только `limit ≤ 500`, без
  offset или курсора, так что 501-й участник недоступен. Модель называется `PageOut`, но
  пагинации в ней нет.
- `public_board` строит полный лидерборд и режет `[:limit]` в Python
  (`services/results.py:32-36`). Если текущий участник не попал в top-`limit`, своей строки
  он не увидит. Стоит возвращать его строку отдельно.
- `update_participant_access` требует `round_id` и берёт `FOR SHARE` на раунд, хотя
  блокировка глобальная для учётной записи. Без раунда (сразу после `restart`, до создания)
  заблокировать участника нельзя.
- В `scoring_run.run` `except Exception` превращает в `scoring_failed` и ожидаемые
  `Conflict` вроде `model_version_mismatch`: организатор видит «ошибка скоринга» вместо
  понятной причины. Стоит пробрасывать `ApplicationError` с исходным кодом.

### 3.3 UI

- `storage["workspace_play"]` хранит запись на каждый `tab_id` и никогда не чистится
  (`participant.py:545-552`); `storage["pages"]` в `page_owner` растёт так же
  (`app.py:44-53`). У активного пользователя за мастер-класс набираются десятки записей в
  JSON-файле хранилища, которые перечитываются и переписываются на каждое сохранение.
  Стоит ограничить их по числу или возрасту.
- `participant.py` — 1269 строк, `organizer.py` — 727: рендер, состояние и сетевые вызовы
  перемешаны. Если вынести `GameEditor` (состояние и API) отдельно от виджетов, станет
  возможна точечная перерисовка (п. 6.4 нагрузочного отчёта) и тесты без NiceGUI.
- Ruff `B023` (`participant.py:1053,1064,1074`): замыкание `update` захватывает `config`
  из цикла. Сейчас `config` одинаков для всех шагов, поэтому бага нет, но при любом
  рефакторинге он появится. Стоит передать `config=config` как параметр по умолчанию,
  как уже сделано для `step_id` и `k`.
- `APIError` объявлен как `@dataclass` поверх `Exception` (`client.py:17-27`): у
  исключения пустые `args`, и в логах и `repr` traceback нет текста. Стоит вызывать
  `super().__init__(message)` в `__post_init__`.

### 3.4 Версионированный и мёртвый код

В `services/` одновременно живут `aml_dataset_features` v1–v5, `aml_game_pattern_panel` и
`_v2`, `aml_game_window_model` и `_v2`, `aml_risk_model`, `aml_probability_model`,
`aml_pattern_model`, `model_scoring.ProbabilityScorer` и `game_classifier.GameClassifier`.
Часть обслуживает сохранённые раунды (так задумано: «прежние раунды сохраняют
закреплённые модели»), но:

- `restart` удаляет все сценарии и раунды (`admin_rounds.py:197-200`), а раунд в системе
  один (`uq_rounds_single_game`). Значит, «старых раундов» после перезапуска не остаётся,
  и поддержка старых пакетов нужна только для одного текущего раунда. Стоит проверить,
  какие пакеты реально закреплены в проде, и удалить остальные вместе с кодом;
- `ProbabilityScorer` (explanation v4) при диспетчеризации `get_round_scorer` не
  выбирается никогда: v10 уходит в `GameClassifier`. Похоже на мёртвый код;
- `scripts/` — 140 файлов, 296 импортов из `src`. Скрипты подготовки датасетов стоит
  отделить от эксплуатационных (`seed_database`, `clear_installation_rounds`), например
  `scripts/ops/` и `scripts/research/`.

### 3.5 Репозиторий

- `resources/` — 1,3 ГБ (LFS): 12 кандидатов `experiment-v1`, 10 в `experiment-v2`,
  `reproduced.cbm`, несколько draft/reviewed-версий датасетов. В рантайме нужны 4–5 пакетов.
  Исследовательские артефакты стоит вынести в отдельный LFS-репозиторий или релизные
  ассеты, иначе каждый `git lfs pull` и CI тянут гигабайт.
- `docs/verification/` — 240 файлов, включая `.log`, `pytest.xml`, `.ipynb`, `.py`.
  Исполняемые скрипты (`audit_operation_purposes.py`, `db_roundtrip.py`) в `docs/` не
  проходят ruff и тесты. Стоит оставить в `docs/` итоговые отчёты, а сырые логи перенести в
  артефакты CI.
- `resources/catboost_models/*/training-pipeline.py` — копии кода обучения внутри
  артефактов. Для воспроизводимости полезно, но это уже не исходник: достаточно ссылки на
  коммит.

### 3.6 Статический анализ

`ruff.toml` включает только `E4, E7, E9, F`. Прогон с `B, SIM, UP, ASYNC` по `src/`:

```
44  B008   function-call-in-default-argument   (в основном Depends — нормально для FastAPI)
23  B905   zip-without-explicit-strict
 3  B023   function-uses-loop-variable          (см. 3.3)
 2  ASYNC109 async-function-with-timeout
 ... всего 96
```

Стоит включить `B` (с исключением `B008` для роутеров), `ASYNC` и `UP`. `zip(strict=True)`
в `model_scoring.py:112` и `game_classifier.py` защитит от молчаливого расхождения
списка признаков и SHAP-вектора.

Типизации нет: `mypy`/`pyright` не настроены, многие функции без аннотаций
(`scoring_service._evaluate`, `game_classifier.*`, `model_scoring.*`). Для кода, где
структура `explanation` проверяется вручную, это особенно заметно.

### 3.7 Мелочи

- Версия `"2.0.0"` захардкожена в двух местах (`api/main.py:36`, `health.py:30`).
- Много импортов внутри функций (`admin_rounds.py:51,162,187`, `health.py:43-44`,
  `scoring_service.py:61,112`), местами без нужды: циклов, которые они обходят, не видно.
  Стоит проверить и поднять наверх, где цикла нет.
- `health_ready` на каждый вызов разбирает каталог миграций через `ScriptDirectory`
  (`health.py:21-24`); результат стоит закешировать.
- `get_db` делает `rollback` только при исключении и надеется, что вызывающий сам сделает
  `commit`. Read-only эндпоинты держат транзакцию до закрытия сессии, это нормально, но
  контракт стоит записать в docstring.
- Комментарии на двух языках вперемешку (`authentication.py`, `health.py`). Стоит выбрать один.

## 4. Что сделано хорошо

Для баланса: основа крепкая.

- Сессии — непрозрачные 32-байтные токены, в БД лежит только SHA-256; `bcrypt_sha256`
  снимает усечение на 72 байтах; есть фиктивный хэш против тайминга для неизвестного email.
- Идемпотентность сохранения и отправки через `client_mutation_id` + `payload_hash` и
  оптимистическая конкуренция через `expected_revision`, в том числе для доступа участника.
- Аккуратные блокировки: `FOR SHARE` на раунд для участников, `FOR UPDATE` для
  администратора, advisory lock для singleton-раунда, уникальный индекс `(true)`.
- Скоринг устойчив к сбоям: приём закрывается отдельным коммитом, частичный расчёт
  откатывается через `begin_nested`, повтор возможен.
- CPU-работа модели вынесена в `asyncio.to_thread`, сессия БД в поток не передаётся.
- Модель закрепляется за раундом (`risk_model` pin), и SHAP проверяется на аддитивность.
- Docker: непривилегированный пользователь, read-only `/app`, БД и API только на loopback,
  секреты обязательны (`${VAR:?}`).
