### AUD-01 · P2 · Запоздавшая загрузка карточек перезаписывает актуальное состояние редактора

**Код:** [game.py](../../../src/aml_workshop_simulator/ui/nicegui/game.py), строки 85–117, особенно `await` на 94/102 и последующие присваивания.

`GameEditor.poll()` проверяет номера чтения/записи после получения `current/state`, затем отдельно ожидает `/cards`. После второго ожидания проверка актуальности отсутствует. В это время другой poll или save может уже завершиться.

**Воспроизведены два случая:**

1. Poll A получает раунд 1 и ожидает карточки. Poll B полностью загружает раунд 2. После завершения A ключ записи остаётся `[2, 1]`, но `state`, карточки и шаги относятся к раунду 1. Следующий poll восстанавливает `state/steps`, **но старые карточки сохраняются**, поскольку список уже непустой.
2. Пока poll ожидает карточки, успешный save сохраняет revision 2 и сумму 150.00. Старый ответ заменяет локальное содержимое revision 1 / 100.00; `dirty=False`, `conflict=False`. Серверная запись при этом остаётся revision 2 — потеря данных в БД этим экспериментом не установлена.

**Последствия:** устаревший экран без сигнала конфликта, возможный выбор карточек не того раунда, дальнейшие конфликты ревизий и непредсказуемое редактирование. Конкурентные входы существуют через poll, reconnect и retry.

**Рекомендация:** получать ответы в локальные переменные; после всех `await` повторно проверять `poll_sequence`, `write_sequence` и принадлежность раунду, затем применять согласованный снимок без промежуточных ожиданий. Проверка только после `self.cards = await ...` недостаточна: карточки уже перезаписаны. Добавить обе последовательности в регрессионные тесты.

**Доказательства:** [ui-race-repro.py](ui-race-repro.py), [ui-race.json](ui-race.json). Используется реальный неизменённый `GameEditor`, без сети/БД и случайных таймеров. Имеющийся тест задержанного `current/state` не покрывает более позднее ожидание карточек.

### AUD-02 · P2 · Недопустимые настройки авторизации принимаются без валидации

**Код:** [core/config.py](../../../src/aml_workshop_simulator/core/config.py), строки 19–21; [authentication.py](../../../src/aml_workshop_simulator/services/authentication.py), строки 112–115 и 141.

`SESSION_TTL_MINUTES`, `LOGIN_MAX_FAILED_ATTEMPTS` и `LOGIN_LOCKOUT_MINUTES` объявлены обычными `int`, без допустимого диапазона. `Settings` принимает 0 и отрицательные значения.

**Подтверждено через настоящий API и PostgreSQL:**

- `SESSION_TTL_MINUTES=0`: `/auth/login` отвечает 200 и выдаёт токен, но `/auth/session` сразу отвечает 401 `session_expired`.
- `LOGIN_MAX_FAILED_ATTEMPTS=1`, `LOGIN_LOCKOUT_MINUTES=-1`: три неправильных входа подряд возвращают 401, хотя после первого должна действовать временная блокировка; 429 не возникает.

**Условие:** ошибка или неподходящее значение в конфигурации окружения. При текущих положительных настройках этот дефект не проявляется; удалённый пользователь не может менять эти значения через API.

**Рекомендация:** определить допустимые положительные диапазоны и валидировать их при старте через Pydantic `Field`. Если отключение ограничений действительно нужно, задать ему отдельный явный контракт. Проверять не только парсинг настроек, но и поведение login/session/lockout.

**Доказательства:** [settings-checksums.json](settings-checksums.json), [test_audit_probes.py](test_audit_probes.py), [settings-api-probes.log](settings-api-probes.log). Пробы меняли только настройки тестового процесса.

### AUD-03 · P2 · Обучение записывает зависимости постороннего Python-окружения

**Код:** [behavior_model.py](../../../scripts/behavior_model.py), строка 351; [catboost_pipeline.py](../../../scripts/catboost_pipeline.py), строка 281.

Обе функции вызывают `subprocess.check_output(["python", "-m", "pip", "freeze"])`. Исполняемый файл определяется отдельно от интерпретатора, который выполняет обучение. При этом `environment.json` описывает текущий процесс, создавая несогласованный набор metadata.

В текущем окружении вызов реально выбирает базовый uv Python 3.13.15 вне `.venv` и сохраняет **пустой `environment.txt`**, хотя активная `.venv` содержит CatBoost 1.2.10, NumPy 2.5.3 и pandas 3.0.5. Пустой результат принимается как успешный. Сбой дочернего `python/pip` останавливает обучение после создания части output-файлов; повтор с тем же каталогом отклоняется.

**Последствия:** по артефактам нельзя достоверно восстановить зависимости обучения; в окружении без доступного `pip` исправное ML-окружение может вообще не дойти до обучения.

**Рекомендация:** получать зависимости активного интерпретатора и сохранять его путь/`sys.prefix`; проверять наличие критичных пакетов в metadata. Простой переход на `sys.executable -m pip` здесь недостаточен: `.venv`, созданная через uv, не содержит pip. Нужен поддержанный способ без этого предположения либо явная установка pip. Проверять сбор provenance до создания output-каталога или явно поддержать неуспешные запуски.

**Доказательства:** [ml-provenance.md](ml-provenance.md), [ml-provenance.json](ml-provenance.json), [repro_ml_provenance.py](repro_ml_provenance.py). Выполнено 6 изолированных проб реальных функций, без обучения. Исторические Linux-артефакты и качество текущей модели этим дефектом не объявляются повреждёнными.

### AUD-05 · P3 · В optimized mode проверка модели выдаёт успех на неполном наборе

**Код:** [verify_model_integration.py](../../../scripts/verify_model_integration.py), строки 40 и 52; безусловное `passed=True` на строке 43 и запись отчёта на 54.

Обязательные проверки количества 4413, полноты эталонов, точности и временного порога реализованы через `assert`. Python исключает их при `-O` или `PYTHONOPTIMIZE=1`.

**Воспроизведение:** создан временный набор из одной настоящей test-строки, использованы реальный scorer и полный файл predictions. Обычный запуск завершился с `AssertionError` без отчёта. Оба optimized-запуска завершились с кодом 0 и записали `passed:true, rows:1`.

**Условие и последствия:** дефект проверочного инструмента проявляется при включённой оптимизации Python и может создать ложное свидетельство приёмки. Полную проверку 4413 строк в обычном режиме, выполненную в этом аудите, он не опровергает.

**Рекомендация:** заменить обязательные quality gates на явные `if ...: raise ...`, записывать успешный отчёт только после всех проверок; добавить негативный тест на неполный набор с `-O`.

**Доказательства:** [optimized-verification.md](optimized-verification.md), [optimized-verification.json](optimized-verification.json), [repro_optimized_verification.py](repro_optimized_verification.py). Основной отчёт полной верификации не изменялся этим экспериментом.

Формального production SLO не задано, поэтому числа не объявлены отдельным багом.
- В Linux-контейнере тот же тест 50 контроллеров дал median 1358 мс, p95 2464 мс, скоринг 2756 мс. Проверка 100 сценариев заняла 6.40 с, максимальная задержка чтения состояния 0.065 с. Это отдельный запуск в другой среде; строгий сравнительный benchmark Windows/Linux не проводился.
- В tracked-файлах не обнаружены конфигурации GitHub Actions/GitLab CI/Azure Pipelines/Jenkins. Локальные проверки полезны, но их обязательный запуск на каждом изменении этим репозиторием не подтверждён. Рекомендуется автоматизировать lint, конфигурацию, unit/ML и API на PostgreSQL; тяжёлую полную верификацию модели запускать отдельно.
- Bandit выдал только low-находки: `random.Random` используется для воспроизводимой синтетики; B105 попал на текст подсказки «Пароль должен содержать…», не на секрет; subprocess-находки разобраны в AUD-03; `assert` в проверочных инструментах требует отдельного внимания к optimized mode. Эти 65 предупреждений не равны 65 подтверждённым уязвимостям.
- `pip-audit` не обнаружил известных уязвимостей на момент запуска. Проверен runtime lock с Windows-маркерами, без пропусков по его результату; это не аудит системных пакетов контейнера или доказательство отсутствия неизвестных уязвимостей.
- Текущие API-тесты покрывают роли и аудитории сессий, блокировки участников, ревизии, повторные команды, конкурентный доступ, атомарность/повтор скоринга и формы NiceGUI. Найденная AUD-01 показывает конкретный пробел: в тестах нет задержки второго запроса `cards`.

## Ограничения этой проверки

1. **Контейнерный стенд локальный:** оба Dockerfile и Compose проверены на Docker Desktop/WSL Linux x86_64. Не проверены другие архитектуры, отдельный production-хост и реальный HTTPS reverse proxy; nginx-конфигурация только просмотрена.
2. **Браузерная проверка ограничена формами входа/регистрации и завершённой игрой участника:** подтверждены результат, SHAP, reload и рейтинг. Полная ручная сборка сценария, панель организатора после входа, мобильные размеры и несколько настоящих браузеров не проходились. Игровые пути и формы дополнительно проверены через API/NiceGUI-тесты.
3. **Dump/restore проверен на двух масштабах:** пустая seeded БД и контейнерная БД с одним завершённым сценарием, сессиями и SHAP. Восстановление большого production-дампа и аварийное восстановление после повреждения файлов не проверялись.
4. **Текущий production-контракт и текущие данные имеют приоритет:** старые экспериментальные датасеты/модели охвачены соответствующими тестами и просмотром tooling, но каждый архивный датасет не прогонялся заново полностью.
5. Не выполнялись внешний pentest, длительный soak test, тест отказа диска, принудительное убийство PostgreSQL и нагрузка на реальный production-сервер.
