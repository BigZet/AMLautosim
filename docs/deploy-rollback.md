# Переход с текущего production и откат

Подготовлено 2026-09-27. Деплой не выполнен. Новая версия запускается отдельным
Compose-проектом **green**; установленная сейчас версия **blue** сохраняется
вместе с её образами, конфигурацией, БД и NiceGUI storage. Возврат маршрута на blue
не требует обратной миграции. Старый Git-тег не доказывает, что именно он на проде.

## Граница отката и данных

Текущий выпуск содержит только модель v10. Старые игры могут быть несовместимы.
Для этого перехода green получает новую пустую БД и новую игру; старые аккаунты,
игры и результаты остаются в blue. Перенос аккаунтов/данных, если понадобится,
требует отдельной проверки на копии. Не запускать seed или Alembic новой версии
на blue и не подключать две версии приложения к общей БД.

Откат доступен, пока сохранено и проверено всё окружение blue. Это не обещание
автоматически перенести записи из green в старую схему: после открытия записи
данные двух версий расходятся. При откате green сохраняется для выгрузки и
сверки; пользователи возвращаются к состоянию blue на момент переключения.
До открытия записи можно проверить переключение туда и обратно без этого риска.
Срок удаления blue устанавливается отдельно; до этого запрещены prune образов,
удаление томов и `compose down -v` для обоих production-проектов.

## До переключения

1. Зафиксировать новый код отдельным commit после всех проверок. CI этого SHA
   должен пройти. Запустить `Release image` для того же SHA; взять registry digest
   из `release-provenance`, сверить OCI revision. Локальный preflight-образ с
   `GIT_SHA=development` предназначен только для проверки.
2. Повторить инвентаризацию установленного прода: Compose project, каталог и
   файлы запуска, контейнеры всех ролей, их image IDs/RepoDigests, команда запуска,
   mounts/volumes, версия PostgreSQL, ревизия Alembic, модель, маршруты LB и DNS.
   Результаты `docker inspect` и `compose config` содержат секреты: хранить только
   в приватном каталоге с `umask 077`, вне Git и общедоступных отчётов.
3. Сохранить **все фактически используемые образы blue**, включая БД и proxy.
   Если registry digest отсутствует, присвоить image ID локальный rollback-tag
   и выполнить `docker image save --output blue-images.tar <tags...>`.
   Зафиксировать соответствие service → image ID → tag и SHA-256 архива.
   Сохранить старый checkout, Compose, env/secrets, proxy/LB-конфигурацию и
   приватный NiceGUI storage. Не собирать старую версию заново из исходников.
4. Сделать backup blue средствами PostgreSQL совместимой версии, сохранить
   manifest с точной ссылкой на старый образ, SHA-256 и проверенную off-host копию.
   Использовать `scripts.ops.backup_database` с `--directory /private/blue-backup`,
   `--image-reference <blue-image-id-or-digest>`, `--container <blue-db-container>`
   и `--offhost <backup-host>:/private/blue-backup`. Соединение — через PG-переменные
   и credential store, без паролей в командной строке. Deployment backup хранить
   отдельно от ежедневной ротации, без `--prune`.
5. В изолированном окружении выполнить `docker image load --input blue-images.tar`
   и восстановить копию blue-БД. Запустить **старые** образы с копиями старой
   конфигурации, проверить вход обеих ролей, игру, сохранённые сценарии и результаты.
   Утилита `restore_database` ожидает текущую структуру таблиц; для старой схемы
   сначала проверить её совместимость, иначе использовать штатный `pg_restore`
   в новую пустую БД и процедуру отзыва сессий старого выпуска. Зафиксировать
   фактическое время восстановления. Наличие дампа без такого drill недостаточно.
6. Проверить свободные диск/RAM/CPU для двух окружений и backup, свободные порт
   и /24 подсеть. На 2026-09-25 был зафиксирован backend `94.241.141.158:8080`,
   LB `80.90.184.166`; эти значения и его source IP требуют повторной проверки.

## Запуск green (Linux, из нового checkout)

Создать приватный `/secure/aml-green.env` по `deploy/.env.production.example`.
Заполнить секреты и `AML_IMAGE=ghcr.io/bigzet/amlautosim@sha256:<проверенный digest>`.
Использовать отдельные секреты storage/auth и БД; `PASSWORD_ARGON2_ENABLED=false`.
Пример: `UI_PORT=8081`, `AML_NETWORK_PREFIX=172.30.24`, `INGRESS_BIND=0.0.0.0`.
Порт, подсеть и имя проекта — примеры, сначала проверить отсутствие конфликта. Старый 8080
остаётся за blue. Не расширять allowlist nginx для удобства проверки.

```sh
set -eu
green() {
  docker compose --project-name aml-green-20260927 \
    --env-file /secure/aml-green.env -f deploy/compose.production.yml "$@"
}
green config --quiet
green pull
green up -d --wait db
green run --rm release
green up -d --no-deps --wait api ui scoring-worker ingress
green ps
green exec -T api python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health/ready').read().decode())"
green exec -T ingress wget -q -O - http://127.0.0.1/health/live
```

`--project-name` отделяет сети и оба именованных тома; `AML_NETWORK_PREFIX`
согласованно меняет статические адреса и trusted CIDR. Не переиспользовать volumes
blue. У worker нет отдельного healthcheck: статус running не заменяет проверку
расчёта. В green через организатора создать тестовую игру, участника, сценарий,
отправить его, запустить расчёт и дождаться результата.

Проверить локаль новой БД: `SELECT lower('Ёлка') = 'ёлка';` должен вернуть `true`.
Официальный Linux-образ PostgreSQL 16 в проверке использует Unicode-совместимую
локаль. Локаль `C` не обеспечивает регистронезависимый поиск русских имён;
не переносить настройки локального Windows-кластера в green.

Проверить green по отдельному TLS test-route на доверенном LB: регистрация/вход,
все типы операций, атрибуты и автосохранение после reload, мобильная ширина,
правая панель, WebSocket reconnect, расчёт/результаты. Прямой внешний запрос
к green должен вернуть 403, API/DB не должны иметь опубликованных портов.
Проверить HTTPS redirect и Secure cookie. Тестовую игру удалить/перезапустить
штатно перед открытием доступа. Пробный маршрут не должен отправлять участников
одновременно в blue и green.

## Переключение

1. Закрыть внешние новые сессии/запись на время окна, дождаться автосохранений
   и активных расчётов blue. Остановить старые API/UI и все фоновые writers
   командами **сохранённого старого Compose**, БД оставить. Закрытие маршрута само
   по себе не разрывает уже открытые WebSocket — остановка writers обязательна.
2. Сделать финальный backup blue и копию storage после остановки writers.
   Зафиксировать UTC-время границы данных. Не удалять старые контейнеры/тома.
3. Изменить единственный активный backend на LB с blue на green (например,
   порт 8080 → 8081), сохранив точную старую конфигурацию для обратного изменения.
   Конкретная команда зависит от актуального провайдера/LB и фиксируется после
   инвентаризации; не менять DNS, если достаточно backend-порта.
4. Пока внешняя запись закрыта, проверить публичный TLS маршрут и новую revision,
   выполнить пробный возврат на blue и снова на green, проверить обе версии.
   Открыть запись только после успешного rehearsal и проверки фонового расчёта.
5. Наблюдать ошибки, readiness, очередь scoring, автосохранение и latency.
   Незавершённые задачи, потеря сохранений, ошибки входа или устойчивые 5xx —
   основания для отката. Вход после переключения может потребовать новой сессии.

## Откат на сохранённый blue

1. Закрыть внешний доступ/запись; дождаться сохранений и завершения расчётов
   насколько позволяет инцидент. Выполнить `green stop ui api scoring-worker`.
2. Сохранить БД и storage green, журналы и время остановки. Не восстанавливать
   blue-backup поверх green; новые записи нужны для последующей сверки.
3. Запустить сохранённые API/UI/worker blue их **исходным** Compose/env, без
   release/seed/миграций и без пересборки. Проверить локальное здоровье и игру.
   Если окружение утрачено — использовать заранее проверенное восстановление
   из архива образов, конфигурации и blue-backup в отдельные тома.
4. Вернуть сохранённый backend-маршрут LB на blue; проверить вход, черновик,
   результаты и WebSocket через публичный HTTPS. Открыть доступ.
5. Green оставить остановленным и сохранённым. Зафиксировать интервал новых
   записей green и план их выгрузки/сверки; автоматического merge БД нет.

## Что ещё требуется на сервере

Заполненная актуальная инвентаризация, off-host backup и успешное восстановление
именно установленной blue-версии, точные команды смены/возврата LB-маршрута,
registry digest нового commit и проверка TLS/perimeter. Локальные проверки
не заменяют эти действия и не означают, что production уже готов к переключению.
