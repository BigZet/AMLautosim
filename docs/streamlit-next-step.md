# Следующий этап: Streamlit как UI

Текущий UI ещё использует удалённые API. До его обновления новая версия ядра
не является готовым к проведению игры полным стеком. Этот файл — план следующего
этапа; код Streamlit сейчас намеренно не изменён.

## Экран участника

1. После входа получать экран через `GET /api/v1/rounds/current/state`.
   Ответ содержит раунд, собственный сценарий, результат и разрешения.
   При смене ID очищать локальные шаги, кеш preview, ревизию и отложенные команды.
2. В `draft` показывать ожидание. В `active` получать карточки через `/cards`.
   Каталог кешировать по ID игры и `config_version`; лидерборд читать отдельно.
3. Если сценарий отсутствует, открыть пустой редактор с `expected_revision=0`.
   Если статус `editing`, восстановить `steps` и `revision` с сервера.
4. После изменения цепочки отправлять `PUT /rounds/{id}/scenario` с
   `expected_revision`, новым UUID `client_mutation_id` и полным `steps`.
   Убрать `label`, историю версий, восстановление и кнопку сохранения черновика.
5. Отправлять автосохранения последовательно, объединяя изменения, накопившиеся
   во время запроса. Сохранять ревизию из ответа. Карточки создаются с базовыми значениями;
   сохранять эти значения так же, как явно введённые участником. При сетевом повторе использовать
   тот же UUID и тот же payload; при конфликте загружать серверное состояние,
   не перезаписывая его автоматически старой локальной копией.
6. Показывать «Сохранение…», «Сохранено» или ошибку. Гарантируется восстановление
   последнего подтверждённого сервером состояния. Не обещать сохранение клика,
   который ещё не дошёл до сервера; обрабатывать обновление вкладки при активном
   запросе явно. Для этой части отдельно выбрать поведение UI на следующем этапе.
7. Preview получать только через `POST /scenario/preview`. Не рассчитывать
   баланс, ограничения или право отправки в Streamlit.
8. Кнопка «Отправить» вызывает `POST /scenario/submit` с полной текущей
   цепочкой `steps`, последней известной `expected_revision` (0 без сохранения)
   и новым UUID `client_mutation_id`. Дополнительный PUT перед отправкой не нужен.
   Остановить новые автосохранения на время отправки; не отправлять накопленную
   очередь после успеха. При потере ответа повторять неизменный запрос с тем же UUID.
   При `409 scenario_revision_conflict` перечитать единое состояние и показать
   конфликт; автоматически перезаписывать другую вкладку нельзя. Это возможно
   и при конкуренции с уже отправленным автосохранением.
   `400 scenario_validation_failed` позволяет продолжить сборку.
9. При `submitted` убрать редактор и preview: показать зафиксированную цепочку
   и ожидание результатов. `409 scenario_submitted` при запоздавшей записи
   приводит к повторному чтению сценария.
10. При завершении игры: участник со сценарием видит цепочку, оценки и лидерборд;
    участник без отправки — только лидерборд. `/scenario` и `/result` вернут
    `null` для участника без отправки.

Ответ `/result` теперь содержит `scenario_id`, `scores`, `rank`, `explanation`,
`resources`. `scores` содержит `risk_score`, `risk_label`, `stealth_score`,
`resource_score`, `game_score`. Полей `base`, `effective`, ручных корректировок
и ссылок на версии сценария больше нет.

## Панель администратора

- Получать игру через `GET /admin/rounds/current`; история раундов отсутствует.
- Если игры нет, `POST /admin/rounds` создаёт настройку. Обычно её создаёт seed.
- Базовые настройки: `/admin/game-config/default`, каталог: `/admin/action-cards`.
- Изменять `title`/`game_config` через `PUT /admin/rounds/{id}` только в `draft`.
  Сохранять `config_revision`; отправлять его как `expected_config_revision`.
- Использовать обязательный `operations`; `card_versions`, `preset_id` удалены.
  Снимки карточек и `config_version` формирует сервер; не передавать эти поля обратно в конфигурации. Не импортировать backend-модули в UI.
  Для карточек конкретной игры использовать `GET /rounds/{id}/cards`.
- «Начать»: `POST /admin/rounds/{id}/start` без тела.
- «Запустить скоринг»: `POST /admin/rounds/{id}/score` без тела. Показывать
  ожидание до ответа, блокировать повторный клик. При сетевом таймауте проверить
  текущую игру перед повтором. Повтор завершённого скоринга безопасен.
  При `500 scoring_failed` показать администратору ошибку и `request_id`,
  разрешить повтор расчёта. Для участника приём остаётся закрытым.
- «Новая игра»: `POST /admin/rounds/{id}/restart` без тела. Перед вызовом UI
  явно сообщает об удалении игровых данных. Ответ — новый ID и `draft` с базовой
  конфигурацией; прошлые настройки не переносятся.
- Удалить остановку/возобновление, шаблоны, версии сценариев, ручные оценки,
  историю игр и просмотр неотправленных цепочек.
- Список участников показывает только `none`, `submitted`, `scored`.
  Детальная карточка содержит аккаунт, отправленный сценарий и результат.
- Административный лидерборд содержит итоговые оценки без `base/effective`.
  Учётные записи и блокировка доступа сохраняются. Удалить инспектор сессий и отправку браузерных метаданных.

## Позднее обновление тестов

Проверить автосохранение после обновления вкладки, одну отправку, конфликт двух
вкладок, одновременную отправку и скоринг, ошибку скоринга без повторного открытия приёма, повтор расчёта после
сбоя процесса, пустой скоринг, удаление игровых данных
при перезапуске, сохранение аккаунтов, отбрасывание запросов со старым ID,
отсутствие неотправленных цепочек в административных ответах и работу миграции.
Старые тесты истории версий, шаблонов и ручных оценок больше не соответствуют
продукту. Старый набор тестов не запускался и не переписывался. Отдельно выполнена HTTP-проверка нового ядра на PostgreSQL: автосохранение, валидация, одна отправка, закрытие, сброс, конкурирующие записи и откат/повтор скоринга.

## Карточки без повторов и полный контракт API

- Одна карточка — одна транзакция. Убрать `frequency`, `show_frequency`,
  `max_frequency` и соответствующие элементы управления. API отвергает их.
- Чтобы выполнить операцию трижды, создать три карточки с разными `step_id`.
  Базовый `max_identical_steps` теперь 3. `max_occurrences` — общий лимит
  карточек данного типа за раунд; это прежний `round_frequency_limit`.
- Использовать `can_edit`, `can_submit`, `blockers` из ответа сценария.
  Preview тоже возвращает `can_submit`. После отправки оба разрешения false.
- Состояние раунда содержит `accepts_changes`; это разрешение приёма в целом,
  а не разрешение редактировать уже отправленный сценарий.
- `objective.reached` — единственный признак достижения цели; остатки после
  шага находятся в `resources_after`. Удалены дубли `goal_reached`,
  `balance_after`, `energy_after`, `time_after`.
- Полные модели ресурсов, параметров, снимка настроек, оценок и ошибок
  доступны в OpenAPI. Настройки для редактирования — `GameConfigIn`,
  снимок ответа — `GameConfigOut` с серверными полями.
- Общая ошибка имеет контракт `ErrorEnvelope`, включая структурированные
  `details.violations` и актуальную ревизию при конфликте.
- Заблокированные участники показаны администратору внизу с `rank=null`.
  Места остальных совпадают с публичным лидербордом.

Формула среднего риска остаётся временной. Из неё удалён только нулевой вклад
от упразднённых повторов. CatBoost-адаптер и генератор датасета не изменялись;
их старые шаблоны с `frequency` нужно адаптировать отдельно перед использованием
с новым игровым движком. Старый Streamlit также пока несовместим с этим API.

## Доступ к рейтингу

Лидерборд доступен только после входа участника; всегда показываются имена.
Убрать переключатель `reveal` и обработку `masked` / `revealed`.
`can_view_leaderboard` из единого состояния разрешает показ завершённого рейтинга.
Администратор использует свой маршрут. Отдельная кнопка закрытия приёма удалена:
«Запустить скоринг» сама закрывает приём, при сбое доступен повтор расчёта.
