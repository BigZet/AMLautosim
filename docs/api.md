# API текущей игры

## Подготовленный контракт вероятности AML (v10, пока закрыт для новых игр)

Создание и запуск новых v10-раундов остаются закрыты до приёмки датасета,
пакета модели и сквозной проверки. Наличие DTO и адаптера не означает выпуск.
Для сохранённых снимков диспетчер различает v8-регрессор и v10-классификатор;
v9 не получает запасную оценку. Серверный `risk_model` v10 закрепляет точные
SHA-256 пакета, модели, калибратора, схемы, порогов и полного контекста раунда.

`ResultOut.explanation` — union по `schema_version`: старый 3 либо новый 4.
В версии 4 `score_kind=aml_probability`, `aml_probability` содержит исходное p,
`risk_score=100*p`, `category` равно `low` при p<0.1, `review` при 0.1≤p<0.9,
`high` при p≥0.9. `context_status` описывает полноту сведений, а не уверенность.
`model_identity`, `context_sha256`, raw margin, калибровка и SHAP сохраняются
вместе с результатом. В `scores.risk_score` остаётся округлённая Decimal-строка.
Совместимые DB-метки normal/review/suspicious не заменяют категорию версии 4.

Строки обоих рейтингов содержат `score_kind`, `leaderboard_version`,
`aml_probability` и `category`. Для старых результатов это `legacy_risk`,
`leaderboard-v2` и два null; для новых — `aml_probability`,
`leaderboard-aml-probability-v1`, сохранённые p и категория. Вероятность нельзя
восстанавливать из округлённой скрытности. GET результата и рейтинга читают БД,
не вызывают модель; повторный завершённый скоринг также возвращает сохранённое.

## Текущий выпуск: CatBoost и SHAP

Новые раунды используют только v8 и CatBoost. Значение по умолчанию для
`/admin/game-config/default`, `/admin/action-cards` и перезапуска — 8; запрос 7
отклоняется. `available_contracts` равно `[8]` или `[]` при запрете новых стартов.
Без `game_config` создание получает расширенные настройки. В сохранённом снимке
добавлен серверный `risk_model`: model_version, model_sha256, extractor,
explanation_version, dictionary_sha256. Клиент не задаёт это поле при обновлении.

Маршруты результата и поля scores сохранены. `explanation` теперь версии 3:
method, model, reference, base_value, raw_score, normalized_score,
clipping_adjustment, rounding_adjustment, additivity_error, factors,
top_positive, top_negative, remaining_contribution, disclaimer. Каждый factor
содержит code, title, description, unit, value, display_value, contribution.
Прежние all_factors/protective_factors не поддерживаются. Полная типизированная
схема публикуется в OpenAPI. Ошибки model_contract_mismatch и
model_version_mismatch — 409; ошибка расчёта — scoring_failed, 500, без частичных
результатов. Описание старых этапов ниже служит историей контракта, не перечнем
доступных режимов текущего выпуска.


Префикс `/api/v1`. Аутентификация — `X-Session-ID`; вход и регистрация сохраняют
существующий контракт. Полные схемы генерируются FastAPI в `/api/v1/docs`.

Все административные маршруты требуют административную сессию. Неотправленные
сценарии не выдаются администратору. Чужие сценарии недоступны через API участника.

Удалены `/active`, `/mine`, список предыдущих раундов, `/activate`, `/stop`,
`/scoring-plan`, `/stats`, история/восстановление сценариев, шаблоны, ручные оценки.
Это согласованное изменение контракта: совместимость со старым UI не сохраняется.

Ошибка имеет поля `code`, `message`, `details`, `request_id`. Ключевые конфликты:
`round_locked`, `round_not_found`, `scenario_submitted`,
`scenario_revision_conflict`, `mutation_id_reused`, `round_config_revision_conflict`.

Настройки нового раунда проходят общую семантическую проверку перед созданием
снимка: поля должны существовать в карточке, итоговые границы сумм — согласованы.
Закрепление скрытых значений не поддерживается.
Ошибка настройки возвращает `409 round_configuration_invalid` без изменения
раунда или аудита. Ту же проверку выполняют запуск FastAPI, seed и
`python -m scripts.validate_config` (включая `--config-dir`); ошибочные файлы
останавливают запуск и seed до записи данных. При переходе на конфигурацию 7 существующую игру следует сбросить;
исторические контракты не поддерживаются.

Порядок вызовов и обработка ошибок описаны в
[описании NiceGUI](nicegui.md).

При ошибке расчёта: `500 scoring_failed`, приём остаётся закрытым. Статусы игры:
`draft` → `active` → `closed` → `scoring` → `completed`.

## Контракты для UI

В Swagger кнопка **Authorize** принимает `session_id` из `/auth/login`;
схема `SessionId` передаёт его в `X-Session-ID`.

`ScenarioStepIn` содержит `step_id`, `card`, `amount`, `context`, `action_details`.
Поля повторов отсутствуют: каждое выполнение — отдельный шаг с новым UUID.
`ScenarioOut` возвращает сохранённые значения, ревизию, ресурсы и
`can_edit`, `can_submit`, `blockers`. Эти разрешения определяет FastAPI.

Ресурсы описаны `ResourceSnapshotOut`, оценки — `ResultOut`, метаданные
карточек — `ActionCardOut`, конфигурация — `GameConfigIn` / `GameConfigOut`.
Произвольный JSON оставлен только для содержимого событий аудита и доказательств
факторов скоринга; структура игровых ответов описана явно.

Схемы ошибок 400/401/403/404/409/422/429/500 заданы как `ErrorEnvelope`.
Readiness использует собственный контракт `ReadyOut`, в том числе для 503.

## Финальная отправка и чтение состояния

`POST /rounds/{id}/scenario/submit` принимает обязательные `steps`,
`expected_revision` (от 0) и `client_mutation_id` (UUID). Сохранение перед
отправкой не обязательно. Валидация, запись сценария и аудит фиксируются одной
транзакцией. Невалидный запрос не изменяет сохранённую цепочку.

Сетевой повтор отправки использует тот же UUID и содержимое; сервер возвращает
зафиксированный сценарий даже после скоринга. Другой UUID или другое содержимое
после отправки дают `409 scenario_submitted`. Конфликт ревизии до отправки —
`409 scenario_revision_conflict`: перечитать состояние, не перезаписывать его
автоматически. Новое содержимое увеличивает ревизию один раз.

`GET /rounds/current/state` возвращает `round`, `scenario`, `result`,
`can_edit`, `can_submit`, `can_view_leaderboard`. Данные и место получены одним
SQL-запросом без блокировок. Если игры нет, три значения равны null,
разрешения false. В открытой игре без сохранения `can_edit=true`,
`can_submit=false`; право отправки текущей локальной цепочки сообщает preview.
Существующие отдельные GET сохранены и используют те же проекции.

Лидерборд участника требует игровую сессию и всегда содержит имена;
`reveal`, `masked`, `revealed` удалены. До завершения расчёта он пуст.
Административный рейтинг остаётся отдельным защищённым маршрутом.

Административный `/close` удалён. `/score` закрывает приём отдельной транзакцией
и запускает расчёт. При ошибке состояние `closed`, доступен повтор `/score`.


## Метаданные NiceGUI-редактора

`GET /api/v1/admin/game-config/editor-metadata` требует административную сессию.
Возвращает EditorMetadataOut: version, schema_version, limits, labels, quotas,
resource_weights, supported_versions, dictionary_keys, overrides. Числовые
ограничения overrides формируются из OperationIn, без второй копии валидаторов.
Семантические ошибки настроек сохраняют 409 round_configuration_invalid и
дополнительно возвращают details.violations с field/reason/message.


## Сокращённый контракт операции

Набор и порядок полей приведены в [балансе игры](../config/BALANCE.md).
`GET /rounds/{id}/cards` возвращает только разрешённые поля в `visible_params`.
У зарплаты `channels=[]`; входящий перевод сохраняет источник `transfer_source`.
Контекст сохранённого шага содержит только применимые ключи, без null-заглушек.
Например, тело шага зарплаты:

```json
{
  "step_id": "00000000-0000-0000-0000-000000000001",
  "card": {"id": 1, "code": "salary", "version": 1},
  "amount": "30000.00",
  "context": {},
  "action_details": {"income_basis": "payroll_registry"}
}
```

`card.id` следует получать из каталога. Передача зарплате канала, времени,
получателя или темпа возвращает 422; также отклоняются все удалённые поля.
Пропущенный применимый контекст заполняется значениями карточки; обязательные
специальные поля должны быть переданы. `resource_rules.amount_adjustment` и
`scoring.rules.amount_adjustment` содержат отдельные поправки суммы.

## Доступность расширенного контракта

V7 остаётся значением по умолчанию. Для новых расширенных игр доступен контракт
v8 с `behavior.release=expanded-game-v1`, полными данными сторон, профиля,
версионированных истории и покупок. Прежние тестовые снимки v8 без release
читаются, но игровые команды для них возвращают `409 round_contract_not_ready`.
Неизвестная версия схемы отклоняется с `422 round_contract_unsupported`.

Скоринг отклоняет недоступный контракт до закрытия приёма и удаления черновиков.
DTO сценария v8 сохраняет ID сторон и интервалы; расширенные шаги в v7
отклоняются (422). В выпущенном v8 доступны preview/save/submit/score и рейтинг.

`EXPANDED_ROUNDS_ENABLED=false` запрещает создание новых v8, сохраняя обслуживание
ранее созданных выпущенных раундов. Переключатель — серверная настройка, не поле
пользовательского сценария. [Отчёт допуска](verification/aml-interface-balance-stage06.md).

## Контрагенты v8 (этап 02)

Каталог сторон передаётся внутри `game_config.behavior.counterparties` и одинаков
для всех участников. Отдельного API изменения сторон участником нет. Поля
`sender_id`/`recipient_id` ссылаются только на этот снимок. Тип стороны и сведения
не принимаются в шаге как ручные характеристики.

В тестовом пути нормализации `counterparty_contract_invalid` означает неизвестную
сторону, неправильную роль/тип, карточку, сумму, канал или производное поле;
`details` содержит `step_index` и `field`. Для v7 расширенные поля возвращают
`scenario_contract_mismatch`. Для прежнего тестового v8 без release запрет срабатывает раньше
семантической нормализации. Неправильная форма DTO отклоняется стандартной 422.

Каталог карточек сохранённого v8 не предлагает `sender_relationship`,
`recipient_type`, ручные темп и время суток. Выбор сторон строится по снимку
`behavior`; временные интервалы реализованы в этапе 03.

[Проверки и ограничения этапа 02](verification/aml-counterparties-stage02.md).

## Временная шкала v8 (этап 03)

Шаг принимает `interval_minutes`: 1, 10, 60, 1440 или null. На первом шаге
каноническое значение всегда null; после первого пропуск/null означает 1 минуту.
Строки, bool, дробные числа и остальные интервалы отклоняются. Производные
`occurred_at`, `elapsed_minutes`, `pace`, `waiting_time_cost` в шаг не принимаются.

В ресурсном ответе v8 добавлен `timeline` с `version`, `timezone` и `steps`.
Каждая строка содержит ID/индекс шага, момент с UTC-смещением, прошедшие минуты,
интервал, `time_of_day`, `pace`, `operation_time_cost`, `waiting_time_cost`.
`per_step.time_cost` равен сумме двух затрат. Snapshot schema — 6;
`ruleset_version` — `expanded-rules-stage03-v1`. Ответы v7 не получают этот блок.

Preview/save/submit используют один расчёт. Для прежних тестовых v8 без release
игровые вызовы возвращают 409; допущенный выпуск описан выше. [Проверки этапа 03](verification/aml-timeline-stage03.md).

## Покупки v8 (этап 04)

Наличие `behavior.purchases` с версией `purchase-policy-v1` включает покупку;
без блока сохраняется поведение этапа 03. `purchase` v1 требует получателя
типа `merchant`, а категорию сервер берёт из каталога сторон. Параметры покупки
фиксированы: 1 000–20 000 ₽, до трёх операций, до 30 000 ₽ суммарно,
энергия 1, базовое время 1, комиссия 0.

Ресурсный snapshot получает `schema_version=7` (контракт раунда остаётся 8),
`ruleset_version=expanded-rules-stage04-v1`, `totals.target_outflow` и
`totals.purchase_outflow`. Общий `gross_outflow` включает покупки без комиссий,
а цель учитывает только переводы и снятия. `per_step.purchase` содержит
`merchant_id` и категорию; `limits` — сумму и количество покупок.

Невыполненная цель при отправке возвращает 400 `scenario_validation_failed`;
ошибки структуры — 422. Вызовы прежних тестовых v8 без release закрыты кодом 409.
Ответы v7 сохраняют прежнюю структуру. [Отчёт этапа 04](verification/aml-purchases-stage04.md).

## Профиль и наблюдаемая история v8 (этап 05)

`behavior.history.version=observed-history-v1` включает строгую проверку событий
за 30 дней до `behavior.timeline.starts_at`, не включая момент начала. Суммы
положительные, конечные, до двух знаков после запятой; даты содержат смещение.
История использует роли сторон тех же операций; категория покупки выводится
из merchant. Неизвестная история — `operations=null`, наблюдаемое отсутствие
активности — `operations=[]`. Независимые агрегаты на вход не принимаются.

`RoundPublicOut` и `RoundAdminOut` получают производный `context_summary` версии
`history-summary-v1`: период, статус, активность, разбивка по операциям, сторонам
и события. При неизвестной истории количественные агрегаты равны null, а не нулю.
`counterparties[].observation` различает observed/absent/unknown; отсутствие
наблюдений относится только к этому периоду. Сводка вычисляется на сервере и
одинакова у всех участников раунда.

Профиль и история меняются только через конфигурацию черновика организатором.
После старта обновление отклоняется (409), у участника нет права записи (403).
Исторические суммы не влияют на текущие ресурсы и цель. Для v7 и прежнего v8
без версии истории поле `context_summary` отсутствует. Для обычного запуска v8 требуется выпуск `expanded-game-v1` (этап 06). [Отчёт этапа 05](verification/aml-profile-history-stage05.md).

## Создание расширенной игры (этап 06)

Контракт API игры не включает офлайн-рубрику или обучение CatBoost. Выпуск
датасета этапа 07 не меняет ответы скоринга: v7 сохраняет `risk-rules-v3`,
допущенный v8 — `expanded-scoring-stage04-v1`.

- `GET /admin/game-config/editor-metadata`: `available_contracts` содержит `[7,8]`
  при разрешении новых игр и `[7]` при отключении.
- `GET /admin/game-config/default?schema_version=8`: новый начальный профиль
  и конфигурация выпуска. Без параметра — прежний v7. При отключении v8 — 409.
- `GET /admin/action-cards?schema_version=8`: пять карточек для редактора;
  без параметра — четыре прежние.
- `POST /admin/rounds`: принимает полную выбранную `game_config` как прежде.
- `POST /admin/rounds/{id}/restart?schema_version=8`: создаёт новый черновик v8
  с новым ID. Без параметра сохраняется прежнее поведение (v7). Это прежняя
  разрушительная команда новой игры: удаляет игровые данные, сохраняя аккаунты.
  Проверка доступности выполняется до удаления. Параметр допускает только 7/8.

У выпущенного раунда нельзя изменить схему или снять release через PUT:
`409 round_contract_immutable`. Отключение создания не запрещает изменение
настроек сохранённого черновика той же версии, его старт, отправку или скоринг.


### Отправитель зарплаты и входящего перевода

Новые расширенные раунды содержат `behavior.sender_policy = "separate-employer-v1"`.
Сторона с категорией `employer` доступна отправителем только для зарплаты;
обычный входящий перевод её не принимает. Другие организации могут отправлять
обычный перевод, но не зарплату. Сервер, редактор и история используют одно правило.
Исходящий перевод работодателю разрешён. Старые снимки без `sender_policy`
читаются и рассчитываются по прежним правилам; их политика не обновляется автоматически.


### Уточнения после аудита интерфейса

Входная конфигурация различается по `schema_version`: ошибка v8 содержит только
ошибки соответствующей ветви. Названия сторон обрезаются по краям, пустые и
пробельные имена отклоняются. Финансовые правила закреплены моделью и остаются
недоступными для изменений. `resources.per_step[].detail_factors` содержит
наблюдаемый параметр и его значение; старые `risk_points` и описание правил
