# План миграции к Streamlit–FastAPI–PostgreSQL

## Исходная точка

Participant UI сейчас использует `streamlit_apps/local_store.py`: учетные записи,
сценарии и результаты живут в памяти Streamlit. Расширенные карточки и правила денег,
энергии, комиссий и зависимостей также находятся в этом модуле. FastAPI и PostgreSQL
уже имеют базовые сущности, auth, раунды, сценарии и скоринг, но их контракты проще,
маршруты не версионированы, а participant UI к ним не подключен.

Миграция не поддерживает длительную работу двух источников истины. `LocalStore` удаляется
после переключения participant UI, без production fallback.

## Этап 1. Зафиксировать контракты

- Утвердить документы `data-model.md`, `api.md` и статусы сущностей.
- Перенести значения карточек из `ACTION_CARDS` в seed-данные PostgreSQL версии 1.
- Описать `GameConfig`, `ActionCard`, `ScenarioStep`, `ResourceSnapshot` и единый error
  envelope как Pydantic-модели.
- Добавить API prefix `/api/v1`, сохранив временную совместимость admin UI на период
  миграции либо переключив его в том же релизе.

**Критерий выхода:** OpenAPI отражает все целевые endpoints и типы, а примеры из
`docs/api.md` проходят schema tests.

## Этап 2. Ввести Alembic и целевую схему

- Инициализировать Alembic и создать baseline для существующих таблиц.
- Добавить версии и игровые поля карточек, `rounds.game_config`, `scenario.revision`,
  `updated_at`, auth lockout и `scoring_version`.
- Перевести денежные поля и расчеты на `Decimal`/`NUMERIC`.
- Создать unique, partial и query indexes из модели данных.
- Сделать idempotent seed карточек и отдельную bootstrap-команду администратора.

**Критерий выхода:** чистая БД поднимается `alembic upgrade head`; upgrade существующей
dev-БД сохраняет данные; downgrade проверяется там, где он безопасен.

## Этап 3. Перенести бизнес-правила в FastAPI

- Создать backend game-rules service на основе текущего `resource_snapshot`.
- Валидировать баланс, энергию, число действий, цель оборота, комиссии, частоту,
  суммы и обязательную предшествующую карточку.
- Использовать одну и ту же функцию для preview черновика и финального submit.
- Сохранить scoring service в backend и связать его с versioned config раунда.
- Добавить unit tests на каждое правило и воспроизводимость scoring.

**Критерий выхода:** backend-тесты покрывают все существующие тестовые сценарии
`test_game_resources.py`, а Streamlit-код больше не нужен для расчета истины.

## Этап 4. Реализовать lifecycle раунда и сценария

- Добавить сохранение/получение черновика и повторную отправку в активном раунде.
- Запретить изменения в `scoring`/`completed`.
- Защитить активацию и scoring row lock и транзакциями.
- Сделать scoring атомарным и идемпотентным для завершенного раунда.
- Добавить stats и board без email.

**Критерий выхода:** интеграционные тесты подтверждают переходы статусов, отсутствие
дубликатов и rollback при ошибке в середине scoring.

## Этап 5. Подключить participant UI

- Вынести HTTP-клиент на `requests.Session` с `st.cache_resource`, timeout и error mapping.
- Перевести регистрацию, вход, active round, cards, draft, submit и result на API.
- Хранить JWT и UI-состояние только в `st.session_state`.
- Сохранять черновик после добавления, удаления, перестановки или подтвержденного
  редактирования шага.
- Использовать локальный preview только для отзывчивости и синхронизироваться с ответом API.
- Добавить разрешенное кэширование active round/cards и явный cache clear.

**Критерий выхода:** перезапуск participant Streamlit не теряет серверный черновик;
пользователь после повторного входа продолжает сценарий.

## Этап 6. Переключить admin UI

- Перевести все пути на `/api/v1` и новую модель конфигурации.
- Добавить редактирование `draft`, preview перед активацией и подтверждение scoring.
- Отображать draft/submitted/scored и duration.
- Обрабатывать неопределенный timeout scoring чтением статуса, без слепого повторного POST.

**Критерий выхода:** администратор проводит полный раунд без обращения к терминалу или БД.

## Этап 7. Удалить автономный режим

- Удалить `streamlit_apps/local_store.py` и импорт backend scoring из Streamlit.
- Удалить локальные регистрации, сценарии и кнопку имитации admin scoring.
- Удалить тесты, проверяющие только in-memory store, после переноса эквивалентных кейсов
  в backend tests.
- При недоступном API показывать управляемую ошибку, не создавать локальные данные.

**Критерий выхода:** поиск по проекту не находит `LocalStore`, `get_store` или локального
вызова `score_steps` из Streamlit.

## Этап 8. Контейнеризация и эксплуатация

- Добавить Dockerfile, полный compose, reverse proxy, сети, health checks и volumes.
- Закрыть API/DB снаружи, настроить TLS и production secrets.
- Добавить structured logging, request ID, live/ready и backup scripts.
- Пройти security checklist и restore drill.

**Критерий выхода:** чистая VM разворачивается по `deployment.md`, извне доступны только
participant/admin UI.

## Этап 9. Приемка

### Автоматические проверки

- Unit: rules, scoring, Pydantic schemas, auth и state transitions.
- Integration: FastAPI + PostgreSQL, транзакции, row locks, unique constraints.
- Contract: примеры API и единый error envelope.
- UI smoke: регистрация, восстановление черновика, submit, result, admin scoring.
- Load: 500 виртуальных участников и одновременная отправка.
- Security: RBAC, IDOR, token expiry, закрытые порты и отсутствие секретов в логах.

### Финальный end-to-end сценарий

1. Создать и активировать раунд с конфигурацией 250 000 ₽, 14 энергии, 8 действий и
   целью 150 000 ₽.
2. Зарегистрировать участников и сохранить несколько черновиков.
3. Перезапустить participant UI и восстановить черновики после входа.
4. Отправить валидные и отклонить невалидные сценарии.
5. Запустить scoring и проверить атомарное число результатов.
6. Сверить participant result, admin board и top factors.
7. Проверить backup/restore и повторный запуск сервисов.

## Откат миграции

До удаления `LocalStore` откат приложения возможен возвратом предыдущего image tag в
dev-среде. После production-переключения откат не возвращает автономное хранилище:
предыдущая совместимая версия должна продолжать читать PostgreSQL. Изменения схемы
выполняются expand/contract, а backup создается перед каждым этапом с данными.
