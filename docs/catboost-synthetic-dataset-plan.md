# Синтетический датасет учебного AML-риска

**Изменение ручной проверки:** по последнему решению пользователя текущий пилот
проверяется на 12 примерах (4+4+4), все сразу и с расчётными баллами.
Обязательная слепая оценка отменена. Упоминания 120+24 ниже относятся к первоначальному
плану/старому прототипу; для текущего выпуска действует
[обновлённый порядок](verification/aml-pilot-stage07.md).

Цель: `CatBoostRegressor`, целевая переменная `target_risk_score` от 0 до 100.
Игрок выполняет цель по обороту и ищет поведение с меньшей оценкой риска.
Метка описывает учебные наблюдаемые сигналы, а не вероятность преступления.

Основа: [обзор источников](aml-behavior-research-2026.md).

## Текущее состояние

Реализованы генератор, отдельная рубрика, extractor и валидатор. Финальный пакет:
48 эталонов, 7 контрольных пар, пилот 2000, релиз 20000. Пользователь проверил 12
случаев и делегировал исправления и завершение. Архивные 24 проверочные цепочки
сохранены без независимых оценок, по решению пользователя они не блокируют выпуск.
На этапе подготовки датасета CatBoost не обучался. Теперь [первая модель обучена офлайн](verification/catboost-training-v1.md), но не подключена к игре. Разделы ниже сохраняют историю исходного плана.

Текущий скоринг, баланс игры, API и существующие 300 примеров не менялись.
Новый extractor `services/aml_dataset_features.py` — отдельный контракт v1;
старый `catboost_features.py` сохраняет совместимость демонстрационных данных.

## Порядок работы

1. Совместно проверить веса и [48 эталонов](../resources/aml_dataset/review-v1/reference_review.md).
2. По результатам внести корректировки в рубрику и повторно получить пакет
   проверки в новой директории. Утвердить конкретные хеши рубрики, эталонов и конфигурации.
3. Сформировать пилот: 2 000 допустимых уникальных вариаций. Проверить 120 записей:
   60 по диапазону риска, 30 около опорных 25/50/75, 30 по расхождению с baseline.
4. Независимо разметить 24 слепые цепочки. Разобрать расхождения; при изменении
   рубрики повторить этапы проверки и пилота. Не подгонять рубрику под challenge.
5. После проверки пилота сформировать релиз из 20 000 уникальных цепочек либо
   документировать недобор. Валидатор проверяет техническое качество;
   окончательное содержательное качество зависит от совместной проверки.
6. Обучение, внешняя валидация и подключение модели — последующие этапы.

## Контракт и ограничения

Все основные цепочки проходят `ScenarioStepIn`, нормализацию, игровой движок и
`submit_blockers` — ту же проверку допустимости, что использует отправка игрока.
Отклонённые варианты хранятся отдельно. Неизвестные структурные значения считаются
ошибкой генератора и прерывают выполнение, а не превращаются в AML-метки.

Три входящих необходимы при действующем балансе и не добавляют риск. Ночные
операции, страна и источник по отдельности также не добавляют баллы. Зарплата
не вычитает риск; её вставка в середину цепочки может изменить наблюдаемую
последовательность. Отсутствие истории клиента не подменяется вымышленным профилем.

Генератор ориентирован на текущие четыре карточки. Распределения сумм и параметров
— явно заданные инженерные допущения, не эмпирическая банковская статистика.
Семейства определяют поисковые мотивы; каждый конкретный эталон требуется проверить
по содержанию, прежде чем считать его подтверждённым представителем типологии.

Разбиение примерно 70/15/15 по группам шаблонов; одинаковые векторы объединяют
группы до разбиения. Константные признаки исключаются по фактической выборке.
Разбиение review-пакета техническое; массовая выборка получает собственный split.

## Воспроизведение

Из корня проекта, используя установленное окружение:

```bash
.venv/bin/python -m scripts.generate_aml_dataset --stage review --output resources/aml_dataset/review-v2
.venv/bin/python -m scripts.validate_aml_dataset resources/aml_dataset/review-v2
.venv/bin/python -m pytest -q tests/unit/test_aml_dataset.py
```

Генератор не перезаписывает существующий каталог. Для воспроизведения той же
версии можно выбрать другой путь; содержательные артефакты будут одинаковыми.
История конфигурации и исходный код должны соответствовать manifest.

После явного согласования пользователем `approval.json` получает `status=approved`
и имя проверяющего, сохраняя хеши просмотренных материалов. Автоматически
согласование не выставляется. Изменение рубрики или эталонов делает запись
согласования неприменимой.

```bash
.venv/bin/python -m scripts.generate_aml_dataset --stage pilot --reference-dir resources/aml_dataset/review-v1 --approval resources/aml_dataset/review-v1/approval.json --output resources/aml_dataset/pilot-v1
.venv/bin/python -m scripts.validate_aml_dataset resources/aml_dataset/pilot-v1
```

Для релиза используются те же `--reference-dir` и `--approval`, а также
`--stage release --pilot-dir resources/aml_dataset/pilot-v1
--pilot-approval resources/aml_dataset/pilot-v1/pilot_approval.json` и новый
`--output`. Перед этим заполняются 120 строк `pilot_review.csv` и 24 строки
`challenge_review.csv`; подтверждается проверка пилота. Это журнал совместного
решения, не механизм удостоверения личности или цифровой подписи.

## Файлы результата

- `scenarios.jsonl`: исходные шаги, ссылка на снимок, полный набор наблюдаемых
  признаков, метки, объяснения, происхождение и диагностический baseline.
- `features.csv`: `scenario_id` для связи и только разрешённые признаки.
  При обучении ID исключается; список входов берётся строго из `manifest.features`.
- `labels.csv`, `splits.csv`: цель и принадлежность группе/части выборки.
- `round_config.json`, `rubric.json`, `generation.json`, `manifest.json`:
  снимки, версии, seed и хеши содержимого.
- `coverage.json`, `quality_report.md`, `dataset_card.md`: покрытие и ограничения.
- `diagnostics.jsonl`: до 200 примеров отклонения; это ограниченная подборка,
  а не статистика доли невалидных операций в реальном мире.

Контрольные признаки не используют текущий `risk_rules.json`. Его значения
остаются в снимке только для воспроизведения baseline. Все основания оценки
сохраняются вне `X`; одинаковые наблюдения получают одинаковые метки.

## Проверки реализации (13.09.2026)

Пакет `review-v1` прошёл валидатор: 48 сценариев, 89 непостоянных признаков,
диапазон предложенных баллов 8,33–63,14. Значения 75–100 в пакете не представлены;
полноту шкалы не имитируем. Проверить её интерпретацию нужно при обсуждении рубрики.

Все 10 тестов нового конвейера прошли, включая воспроизводимость, контроль
изменённых файлов, защиту от несогласованной генерации и тестовый экспорт 120
одноразовых fixtures. Последний использует явно тестовое согласование и не
является реальным пилотом. Ruff и `git diff --check` прошли.

Общий запуск unit-тестов: 98 passed, 1 failed. Падение
`test_incoming_form_exposes_sources_and_sender_without_legacy_frequency` связано
с уже существующим изменением `participant.py`, скрывающим единственный канал:
тест ожидает 5 select, форма создаёт 4. Этот UI-код в рамках датасета не менялся.
Проверки выполнены в установленной `.venv` на Python 3.12.
