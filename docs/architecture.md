# Архитектура ядра

Согласованная модель: одна текущая игра, один сценарий на участника,
одна окончательная отправка. Истории игр, версий сценария, шаблонов
и ручных оценок нет. CatBoost не входит в этот этап изменений.

## Границы

- `api/routers/` задаёт HTTP-контракты и зависимости доступа. Обработчики
  передают в сервисы обычные значения, схемы и сессию БД.
- `services/` реализует прикладные операции: автосохранение, отправку,
  управление игрой, скоринг, выдачу результатов и управление участниками.
- `domain/` содержит модели игры, структурную валидацию, симуляцию ресурсов
  и расчёт оценок. Вычисления получают конфигурацию явно.
- `db/models/` описывает хранилище; `db/queries.py` содержит общие запросы
  и блокировки. Репозитории с дублирующим CRUD удалены.
- `schemas/` определяет Pydantic-контракты. Сервисы могут использовать эти
  модели: отдельные копии DTO ради формального разделения слоёв не нужны.

Общая конфигурация каталога загружается из файлов при инициализации модулей;
проверка файлов выполняется при старте приложения. При подготовке игры
сервер создаёт полный снимок карточек и правил. Расчёт использует этот снимок,
а не запасные значения из изменяемого каталога. Старые форматы не поддерживаются.

## Модули игры

| Модуль | Ответственность |
| --- | --- |
| `domain/game_models.py` | Карточки, правила раунда, нарушения, денежные значения |
| `domain/structure.py` | Контракт шагов и параметров |
| `domain/simulation.py` | Ресурсы, ограничения, возможность отправки |
| `domain/round_policy.py` | Доступные операции и полный контракт параметров |
| `domain/lifecycle.py` | Ограничения изменения состояния и ревизии |
| `domain/scoring.py` | Детерминированные оценки и формула итогового счёта |
| `services/scenario_service.py` | Нормализация и единый вызов оценки сценария |
| `services/scenarios.py` | Автосохранение и окончательная отправка |
| `services/admin_rounds.py` | Подготовка, запуск, сброс игры |
| `services/scoring_run.py` | Закрытие приёма, транзакции скоринга и повтор после ошибки |
| `services/results.py` | Только чтение результатов и лидерборда |

`domain/rules.py` — короткий публичный фасад существующего движка,
используемый сервисами, тестами и отложенным CatBoost-адаптером.

## Состояния

Раунд: `draft` (настройка) → `active` (приём сценариев) → `closed` (приём закрыт)
→ `scoring` (расчёт) → `completed` (результаты доступны).
`draft` относится только к настройке раунда, отдельной сущности черновика нет.

Сценарий: `editing` (временное автосохранение) → `submitted` → `scored`.
Редактирование разрешено только при `active + editing`. Отправленный сценарий
не может вернуться в редактирование. Preview после отправки также недоступен.

Ошибка проверки отправки не расходует попытку. Повтор успешной отправки с теми же UUID и содержимым возвращает уже зафиксированный сценарий, в том числе после скоринга.

Неотправленные автосохранения доступны только владельцу во время игры.
Административные проекции их не показывают. Закрытие приёма удаляет их; скоринг оценивает
только отправленные сценарии. Участник без отправки после завершения видит
только лидерборд. Пустая игра завершается с пустым лидербордом.

Перезапуск удаляет раунд, сценарии, результаты и игровой аудит. Учётные записи
и сессии входа сохраняются. Создаётся раунд с **новым ID**, базовой конфигурацией
и статусом `draft`; администратор настраивает его и нажимает «Начать».
Задержавшийся запрос со старым ID не может изменить новую игру.

## Транзакции и конкуренция

Прикладная операция завершает свою транзакцию. Общие запросы и расчёт скоринга
не делают `commit`. На исключении запрос откатывает незавершённую транзакцию.

Порядок блокировок: раунд → участник → сценарий. Автосохранение и отправка
берут разделяемую блокировку раунда; команды жизненного цикла — исключительную.
Это позволяет разным участникам сохраняться одновременно и исключает запись
сценария поверх завершённого скоринга или перезапуска.

Строка пользователя защищает в том числе первое сохранение, когда сценария ещё
нет. `expected_revision` защищает от устаревшего состояния из другой вкладки.
`client_mutation_id` позволяет повторить последнее автосохранение после потери
ответа. Ревизия — технический счётчик, история содержимого не хранится.

Игра рассчитана на 50 участников. Команда скоринга выполняется в рамках
HTTP-запроса без очереди задач; чистые вычисления вынесены в поток, чтобы
не блокировать обработку запросов на основном цикле событий.

Закрытие приёма — отдельная транзакция: она ждёт уже допущенные записи,
фиксирует `closed_at`, удаляет неотправленные сценарии и делает commit.
После этого возврата к `active` нет. Закрытие вызывается только внутри `/score`; отдельной HTTP-команды нет.

Перед расчётом публикуется `scoring`. Затем обработчик заново читает раунд
под исключительной блокировкой: конкурентная команда могла уже завершить
расчёт или перезапустить игру. Блокировка удерживается до конца расчёта.
Результаты записываются в savepoint внутри этой транзакции. При ошибке
частичные результаты откатываются, раунд остаётся закрытым, а администратор
получает `scoring_error` с `request_id`; traceback остаётся в серверном логе.
После обычной ошибки состояние — `closed`, после обрыва процесса оно может
остаться `scoring`. Повтор `/score` получает освобождённую PostgreSQL блокировку
и повторяет расчёт. Если расчёт уже идёт, повтор ждёт его завершения;
если завершён — возвращает существующий результат. Публикация оценок атомарна.

Уникальный индекс БД ограничивает число раундов одной записью. Создание и
перезапуск также сериализованы advisory-блокировкой транзакции.

## UI и схема БД

NiceGUI — единственный UI; общается с API через HTTP. Контракты и проверки
описаны в [nicegui.md](nicegui.md) и [tests/README.md](../tests/README.md).
Alembic содержит начальную ревизию для пустой БД. Прежняя схема разработки
автоматически не переносится; текущая очистка не меняет формат данных.

Сессии проверяются без записей в БД на каждом запросе. Проверка пароля выполняется
в потоке; строка пользователя блокируется при входе, чтобы конкурентные неудачные
попытки не теряли счётчик. Перед записью сценария повторно проверяется блокировка
участника под блокировкой строки.

## Одна карточка — одна транзакция

Количество выполнений не является параметром карточки. Для трёх операций
хранятся три шага с отдельными UUID. Сумма, комиссия, время, энергия и счётчики
лимитов рассчитываются для каждого шага. Общий предел карточек одного типа —
`max_occurrences`, предел последовательных одинаковых — `max_identical_steps`.

Ресурсный движок независим от временной формулы риска. В симуляции выделены
проверка лимитов операции, расчёт затрат и формирование отчёта об ограничениях.
Псевдоскоринг сохранён, кроме удаления неиспользуемого фактора повторов.

Количественные настройки хранятся в `config/`; выбранные контрольные маршруты
проверяет `scripts/check_game_balance.py`. См. [баланс](../config/BALANCE.md).

## Согласованное чтение экрана

`services/participant_state.py` объединяет раунд, свой сценарий, результат и
место в одном SQL-запросе. Рейтинг вычисляется оконной функцией `dense_rank`
по всем незаблокированным участникам до фильтрации владельца. Этот же запрос
ранжирования применяется в лидербордах. Чтение не захватывает блокировку раунда.
Отдельные GET сценария и результата используют общий сервис состояния.

Окончательная отправка принимает цепочку целиком, валидирует её и фиксирует
в одной транзакции. Существующие поля хеша и UUID обеспечивают безопасный повтор
без отдельной таблицы команд. Предварительное автосохранение не требуется.
