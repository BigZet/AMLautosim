# Архитектура текущего выпуска

Текущий выпуск использует контракт v10 и единственный пакет
`aml-game-organizer-settings-v1`. Его контрольные суммы и состав зафиксированы
в [описании выпуска](current-release.md). Старые игровые модели не поставляются.

У игры один общий контекст и одна окончательная цепочка на участника. Организатор
настраивает разрешённые параметры в черновике; старт фиксирует снимок карточек,
правил, профиля и истории. Проверка пакета связывает модель, признаки и реализацию
вычислений. Отсутствующая или повреждённая модель не заменяется другой.

## Границы

- `api/routers/` задаёт HTTP-контракты и зависимости доступа. Обработчики
  передают в сервисы обычные значения, схемы и сессию БД.
- `services/` реализует прикладные операции: автосохранение, отправку,
  управление игрой, скоринг, выдачу результатов и управление участниками.
- `domain/` содержит модели игры, структурную валидацию, симуляцию ресурсов
  и расчёт оценок. Вычисления получают конфигурацию явно.
- `db/models/` описывает хранилище; `db/queries.py` содержит общие запросы
  и блокировки. Репозитории с дублирующим CRUD удалены.
- `schemas/` определяет Pydantic-контракты. Сервисы могут использовать эти
  модели: отдельные копии DTO ради формального разделения слоёв не нужны.

Общая конфигурация каталога загружается из файлов при инициализации модулей;
проверка файлов выполняется при старте приложения. При подготовке игры
сервер создаёт полный снимок карточек и правил. Расчёт использует этот снимок,
а не запасные значения из изменяемого каталога. Старые форматы не поддерживаются.

## Модули игры

| Модуль | Ответственность |
| --- | --- |
| `domain/game_models.py` | Карточки, правила раунда, нарушения, денежные значения |
| `domain/structure.py` | Контракт шагов и параметров |
| `domain/simulation.py` | Ресурсы, ограничения, возможность отправки |
| `domain/round_policy.py` | Доступные операции и полный контракт параметров |
| `domain/lifecycle.py` | Ограничения изменения состояния и ревизии |
| `domain/scoring.py` | Ресурсная оценка, формула рейтинга и отдельный rule-based расчёт для tooling |
| `services/model_scoring.py` | Проверка пакета CatBoost, оценка риска и объяснения SHAP |
| `services/scoring_service.py` | Объединение модельного риска и ресурсов, сохранение результатов |
| `services/scenario_service.py` | Нормализация и единый вызов оценки сценария |
| `services/scenarios.py` | Автосохранение и окончательная отправка |
| `services/admin_rounds.py` | Подготовка, запуск, сброс игры |
| `services/scoring_run.py` | Закрытие приёма, транзакции скоринга и повтор после ошибки |
| `services/results.py` | Только чтение результатов и лидерборда |

`domain/rules.py` — короткий публичный фасад существующего движка,
используемый сервисами, тестами и CatBoost-адаптером.

## Состояния и хранение

Раунд проходит состояния `draft`, `active`, `closed`, `scoring`, `completed`.
Редактирование сценария разрешено только при `active + editing`. Окончательная
отправка фиксирует всю цепочку; повтор с теми же UUID и содержимым безопасен.
Неотправленные автосохранения доступны только владельцу и удаляются при закрытии.

В БД допускается один текущий раунд. Перезапуск создаёт новый ID, удаляет игровые
данные и сохраняет учётные записи и сессии. Запоздалые команды со старым ID
не изменяют новую игру. Таблицы и миграции описаны в [data-model.md](data-model.md).

## Транзакции и фоновый расчёт

Автосохранение и отправка блокируют раунд, участника и сценарий в согласованном
порядке. `expected_revision` предотвращает перезапись устаревшей вкладкой;
`client_mutation_id` обеспечивает безопасный повтор после потери ответа.

Команда скоринга закрывает приём и создаёт устойчивую задачу в `scoring_jobs`.
Отдельный worker получает задачу и продлевает lease. После потери worker задачу
можно восстановить; проверка владельца и попытки не позволяет устаревшему процессу
опубликовать результат. Результаты всей партии публикуются одной транзакцией.
Ошибка не открывает приём заново. Завершённый результат читается без пересчёта.

API возвращает задачу с HTTP 202. Организатор отслеживает её состояние и прогресс;
параметр `wait=true` оставлен для ограниченного ожидания совместимыми клиентами.
Модельный расчёт и ресурсная симуляция разделены. Preview показывает ресурсы
и нарушения, а вероятность и SHAP доступны только после завершения игры.

## Интерфейс и эксплуатация

NiceGUI общается с API по HTTP и не обращается напрямую к игровой БД.
Сессии участника и организатора разделены. PostgreSQL, API, worker, UI и ingress
запускаются через Docker Compose; release-команда применяет Alembic и seed.
Проверка готовности подтверждает доступность БД и текущего модельного пакета.

Подробности: [API](api.md), [интерфейс](nicegui.md),
[скоринг](scoring-and-leaderboard.md), [развёртывание](deployment.md).
