# Архитектурные решения

Документ фиксирует решения для v1. Изменение решения требует обновить связанные
документы, контракты и readiness checklist.

## D1. Одна облачная VM

**Решение:** reverse proxy, два Streamlit, FastAPI и PostgreSQL работают на одной VM.

**Почему:** нагрузка ограничена 500 участниками, мероприятие короткое, а простота
развертывания и диагностики важнее высокой инфраструктурной сложности.

**Пересмотреть:** недостаточно вертикального масштаба, нужен независимый lifecycle БД,
несколько мероприятий одновременно или требования высокой доступности.

## D2. Docker Compose вместо оркестратора

**Решение:** v1 запускается Docker Compose с разделенными сетями и health checks.

**Почему:** один узел не оправдывает Kubernetes; Compose дает воспроизводимый запуск и
понятный rollback по image tag.

**Пересмотреть:** появляется несколько узлов, автоматическое горизонтальное
масштабирование или централизованная платформа организации.

## D3. FastAPI является внутренним API

**Решение:** браузер обращается только к Streamlit; API доступен из Docker-сети.

**Почему:** уменьшается поверхность атаки, не нужен браузерный CORS, токен не хранится
в browser storage, а PostgreSQL гарантированно находится за API.

**Пересмотреть:** появляется мобильный/внешний клиент или независимый публичный API.
Тогда потребуется отдельный gateway, CORS, публичная документация и усиленные limits.

## D4. PostgreSQL — единственный источник истины

**Решение:** пользователи, конфигурации, черновики, сценарии и результаты хранятся в PG.

**Почему:** данные переживают rerun и перезапуск Streamlit, а транзакции обеспечивают
атомарный scoring и уникальность.

**Пересмотреть:** не требуется. При масштабировании меняется размещение PostgreSQL, но
не его роль. Кэш не становится владельцем данных.

## D5. Синхронный пакетный скоринг

**Решение:** admin POST удерживает запрос до завершения расчета всех submitted сценариев.

**Почему:** текущая объяснимая модель легкая, объем ограничен, очередь и worker увеличат
число точек отказа без измеримой пользы.

**Пересмотреть:** p95 scoring превышает 10 секунд, используется тяжелая ML-модель,
нужны progress/retry задач или параллельная обработка нескольких раундов.

## D6. Email/пароль и JWT

**Решение:** участник регистрируется по email, пароль хранится как bcrypt, Streamlit
держит четырехчасовой access JWT в `st.session_state`.

**Почему:** пользователь может повторно войти после потери UI-сессии и восстановить
черновик; модель уже частично реализована.

**Пересмотреть:** организатор запрещает сбор email, требуется SSO или вход по коду
мероприятия. Для школьной аудитории до пересмотра действует минимизация и срок удаления.

## D7. Версионированные карточки и snapshot раунда

**Решение:** изменения карточки создают новую версию; `game_config` активированного
раунда хранит ID конкретных версий и scoring config.

**Почему:** одинаковый сценарий должен давать воспроизводимый результат после изменения
каталога или запуска следующего мероприятия.

**Пересмотреть:** карточки становятся сложными управляемыми сущностями с отдельным
workflow публикации; тогда возможны normalized round-card tables.

## D8. Контролируемое кэширование Streamlit

**Решение:** `st.cache_resource` только для HTTP client, `st.cache_data` только для
active round/cards с коротким или безопасным TTL. Пользовательские данные не кэшируются.

**Почему:** кэш ускоряет справочники, но не должен смешивать JWT, сценарии и результаты
между Streamlit-сессиями.

**Пересмотреть:** появляется внешний cache layer или измерения показывают, что чтения
справочников создают нагрузку на API/PG.

## D9. Без Redis, Celery и offline fallback

**Решение:** v1 не содержит распределенного кэша, очереди и автоматического LocalStore.

**Почему:** каждый из этих механизмов создает дополнительное состояние и эксплуатацию.
Fallback особенно опасен появлением двух несовместимых источников истины.

**Пересмотреть:** Redis нужен для нескольких VM/rate limiting, очередь — для тяжелого
scoring. Offline-режим может существовать только как отдельный продукт с явным экспортом
и импортом, а не скрытое автоматическое переключение.

## D10. Одна активная игровая сессия

**Решение:** одновременно допускается один раунд в `active` или `scoring`.

**Почему:** v1 обслуживает одно мероприятие, а правило упрощает participant UI,
операторскую работу и общий запуск scoring.

**Пересмотреть:** платформа начинает обслуживать несколько залов или мероприятий;
потребуются event/tenant scope, маршрутизация участника и изоляция admin-доступа.
