# Поэтапное расширение AML-поведения

**Исторический статус: этапы 01–08 завершены.** Реализованы контракты, контрагенты, временная шкала, покупки, профиль и предыстория; выпущен учебный датасет из 20000 цепочек.

Следующий цикл описан отдельно: [аудит смысла операций, интерфейса и разнообразия оценок](09-semantic-and-interface-audit.md). Его работы и критерии не входят в завершённый статус этапов 01–08.

Этот пакет фиксирует последовательность первоначального расширения. После него
принят выпуск только с CatBoost и новой игровой БД: старые раунды не переносятся,
правила риска в онлайн-расчёте не используются. Исторические условия совместимости
ниже не являются условиями нынешнего деплоя. Текущее состояние и замечания:
[интеграция](../../verification/catboost-shap-integration.md),
[аудит](../../verification/full-audit/README.md).

## Цель

Расширить наблюдаемые данные игры: конкретные контрагенты, интервалы операций, покупки и общий профиль с предысторией. Участник по-прежнему выполняет целевой оборот и ищет поведение с меньшей учебной оценкой риска.

[Индекс документации](../../README.md) · [План датасета](../../catboost-synthetic-dataset-plan.md) · [Обзор AML-источников](../../aml-behavior-research-2026.md)

## Порядок внедрения

```text
Контракты → Контрагенты → Временная шкала → Покупки
→ Профиль и история → Интерфейс и баланс
→ Новый датасет → Итоговая проверка
```

Промежуточные изменения проверяются на тестовых конфигурациях. До завершения этапа 06 новую версию нельзя выбирать, создавать или запускать для обычного раунда; ограничение проверяет сервер, а не только интерфейс. После этапа 06 допускаются новые раунды; этап 08 подтверждает полную готовность выпуска, включая документацию и окружение.

Каждый этап выполнять отдельным проверяемым изменением. Следующий начинается после выполнения критериев предыдущего и записи фактического результата. При ошибке оставить статус «в работе» или «заблокирован», записать причину и условие продолжения. Статус «завершён» означает, что обязательные проверки и ручной сценарий выполнены. Исключения описывать явно; документирование исключения не заменяет выполнения обязательного критерия.

## Общие решения и ограничения

- Старые снимки и результаты сохраняют прежнюю интерпретацию; новые возможности применяются только к новым раундам.
- Каталог сторон и профиль общие для участников и неизменяемы после запуска. Игрок выбирает стороны, но не редактирует их свойства.
- Контрагенты, профиль и история находятся в JSON-снимке; отдельные таблицы для них не создаются.
- Покупки уменьшают баланс и расходуют ресурсы, но не входят в целевой оборот.
- Сохраняются стартовые 180 000 руб., 30 единиц времени, 30 энергии и цель 400 000 руб.
- Интервалы 1/10/60/1 440 минут стоят 0/1/2/4 игровых единицы; базовая стоимость операции учитывается отдельно.
- История охватывает 30 дней до начала сценария; будущие события и скрытые преступные намерения не используются.
- Целевая переменная будущей регрессии — учебный риск 0–100, а не вероятность преступления.
- Массовая разметка выполняется только после совместного согласования новой рубрики, затем проверки пилота.
- CatBoost не обучается и не подключается в рамках этого пакета.
- Свои счета, внесение наличных и дополнительные основания переводов отложены.

## Исходное состояние

В проекте есть четыре карточки, детерминированный скоринг и [прототип review-v1](../../../resources/aml_dataset/review-v1/reference_review.md). Этот набор — исходный материал для переработки, не завершённый этап нового внедрения и не согласованная разметка расширенной игры.

В предыдущем запуске unit-тестов зафиксировано: 98 passed, 1 failed. Тест `test_incoming_form_exposes_sources_and_sender_without_legacy_frequency` ожидает пять списков, тогда как ранее изменённая форма скрывает единственный канал и показывает четыре. Это историческое исходное состояние, не результат проверки данного пакета документов. При реализации формы повторить тест и согласовать ожидания с утверждённым поведением; не отключать его.

## Матрица проверок

Команды выполняются из корня репозитория в установленном окружении. Проверки документации при создании этого пакета не являются выполнением тестов будущих этапов.

| Проверка | Когда применять | Команда / инструкция |
|---|---|---|
| Конфигурация | При изменении карточек, параметров и снимков | `.venv/bin/python -m scripts.validate_config` |
| Баланс | При изменении ресурсов, времени, оборота | `.venv/bin/python -m scripts.check_game_balance` |
| Unit | На каждом затрагивающем код этапе | `.venv/bin/python -m pytest -q tests/unit` |
| API и БД | При изменении сохранения, валидации и расчётов | `.venv/bin/python -m pytest -q tests/api`; отдельный `TEST_ADMIN_DATABASE_URL` по [инструкции](../../../tests/README.md) |
| Статические проверки | При изменении Python | `.venv/bin/ruff check src scripts tests migrations` |
| Транспорт | На запущенном тестовом стеке | `.venv/bin/python scripts/check_nicegui_transport.py --url http://127.0.0.1:8080` |
| Новый датасет | Этапы 07–08 | Валидатор и целевые тесты новой версии; точную команду записать в отчёте этапа 07 |
| Контейнеры | Этап 08 | Python 3.13, отдельный Compose-проект и тома по [развёртыванию](../../deployment.md) и [стратегии проверок](../../testing-strategy.md) |

Целевые проверки выполнять после соответствующих изменений; весь обязательный набор — перед итоговым выпуском. При добавлении новых тестов записывать их точные имена. Не сообщать о прохождении тестов, которые не выполнялись. Не повторять дорогие проверки без изменений или нового основания.

## Работа с результатами

Каждый отдельный план содержит чек-лист и раздел фактических результатов. После реализации заполнить дату, версию кода, окружение, команды, коды завершения, автоматические и ручные результаты, ссылку на датированный отчёт в `docs/verification/`, ограничения и решение о завершении. Затем обновить таблицу этапов выше.

Текущую документацию приложения обновлять по мере реализации: не описывать ещё не реализованные поля как доступные. В конце этапа 08 согласовать между собой документацию API, данных, скоринга, интерфейса и проведения игры.

## Отключение нового поведения

До этапа 06 держать новый режим недоступным обычным раундам. При проблемах после допуска запретить создание новых раундов расширенной версии через `EXPANDED_ROUNDS_ENABLED=false`; сохранённые выпуски продолжают обслуживаться. Уже сохранённые раунды обслуживать кодом, понимающим их контракт. Не откатывать приложение на старый бинарный файл без такой поддержки и не переписывать старые снимки для обхода ошибки.

Если проверка баланса выявит недостижимую стратегию, подготовить конкретные расчёты и варианты корректировки новых затрат. Изменение исходного баланса не входит в автоматическое исправление.
