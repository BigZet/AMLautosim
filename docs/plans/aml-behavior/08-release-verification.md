## Цель и границы

Подтвердить совместимость, полный цикл игры и соответствие документации реализованному поведению. Не выдавать техническую проверку за подтверждение качества реального AML.

## Предварительные условия

- Завершены этапы 01–07; доступны их отчёты и список ограничений.
- Подготовлены изолированная PostgreSQL, отдельное контейнерное окружение и тестовая игра.
- Известное исходное падение UI-теста сопоставлено с утверждённым поведением формы.

## Зафиксированные решения

- Контейнерная проверка выполняется на проектном Python 3.13.
- Не использовать рабочую игру и её БД для destructive fixtures или проверок перезапуска.
- Старые и новые контракты проверяются вместе.
- Отключать упавшие проверки ради зелёного отчёта нельзя.

## Последовательность реализации

1. Выполнить проверки конфигурации, баланса, unit- и API-тесты.
2. Выполнить браузерный цикл: настройка, старт, редактирование, reload, отправка, расчёт и рейтинг.
3. Проверить рестарт UI/API, восстановление входа и сохранённой цепочки.
4. Прогнать обе версии контрактов на изолированной БД.
5. Выполнить контейнерную сборку и проверку запуска на Python 3.13 по существующим инструкциям проекта.
6. Обновить документацию данных, API, скоринга, интерфейса и проведения игры по фактически реализованному состоянию.
7. Сохранить датированный отчёт с командами, окружением, результатами и ограничениями; поставить ссылки в общий план.
8. Подтвердить готовность новой версии для новых раундов и работоспособность её отключения.

## Данные, API и интерфейс

- Новых возможностей этот этап не добавляет; устраняет найденные несоответствия реализованных контрактов.
- Документация описывает поддерживаемые версии и поведение при ошибках.
- Совместимый код чтения сохранённых данных остаётся доступным при отключении новых раундов.

## Автоматические проверки

- Конфигурация, баланс, unit и API проходят обязательные проверки.
- Проверки WebSocket/транспорта выполняются для запущенного тестового стека.
- Старые снимки читаются и дают прежние результаты; новая игра корректно восстанавливается после рестарта.
- Валидатор нового датасета проходит; статус человеческой проверки записан отдельно.

Команды брать из [матрицы проверок общего плана](README.md#verification). Новые целевые тесты и точные команды записать в фактические результаты после их появления.

## Ручной сценарий

1. Пройти весь раунд участником и организатором в браузере.
2. Перезапустить тестовый стек между сохранением и отправкой и проверить восстановление.
3. Отключить создание новых раундов новой версии и убедиться, что сохранённые продолжают открываться.

## Отключение при ошибке

Запретить новые раунды расширенной версии. Уже сохранённые раунды обслуживать совместимым кодом; не выполнять откат на старый бинарный файл, который не понимает их контракт. Повторный допуск — после устранения причины и повторения затронутых проверок.
